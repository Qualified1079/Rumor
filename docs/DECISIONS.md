| O11 | **`[DECISION]`** `no-bridged-rerelay` assertion may need escalation** | The scenario runner's `NoBridgedRerelay` check is a post-hoc snapshot scan: at the end of a scenario it walks every node's stored messages and flags any BRIDGED-trust message whose `recipientId` doesn't match that node's `userId`. It's reliable in the simulator because the in-memory `MessageRepository` never evicts during a run, but it would miss a violation where the engine relayed a bridged message, then the message expired or got evicted before the scan. If the in-sim message store ever starts trimming during a scenario — or if this assertion graduates to production telemetry — escalate to a live observer: add a `relayObserver: ((RumorMessage) -> Unit)?` hook to `GossipEngine.relay()` and have the runner subscribe per-node. The current implementation is in `simulator/.../scenario/ScenarioRunner.kt` and is intentionally marked temporary in the JSON-schema docstring on `Assertion.NoBridgedRerelay`. |
| O12 | **`[DECISION]`** `deterministic-replay` residual non-determinism** | `SimTransport.exchange()` was fixed to (a) drop real `delay()` calls and (b) use the tick's seeded RNG. Two variance sources remain: (1) `GossipEngine` runs internal handlers on `Dispatchers.Default`; coroutine scheduling order isn't guaranteed (affects `totalMessages` by ~3–5%). (2) `ConcurrentHashMap` iteration order in `knownMessages()` determines which RNG values the conditioner consumes; drop counts vary by <0.1% across runs. Both are tolerated by ±5% relative bounds on both messages and drops in the assertion. If variance grows, the escalation path is a single-threaded dispatcher for `SimNode.scope` (to fix handler order) and sorting `knownMessages()` by ID (to fix conditioner RNG consumption order). Neither done preemptively — the 5% band keeps the assertion useful as a regression catch. |
| O63 | **`[DECISION]`** iOS via shared `:core` (KMP), not a separate app** | Separate-but-interoperable iOS app rejected: two protocol implementations diverge silently, and the wire is the only place a bug is unrecoverable post-ship. Four hard constraints, in order — do not skip ahead: (1) **stable storage interfaces in `:core` before any SQLDelight migration** — DAOs (Room today, SQLDelight tomorrow, Core Data never) must not leak past the adapter layer; anything in `:core` importing a DAO type is the bug. (2) **`:core` compiles unchanged on JVM, Android, Linux, iOS** — platform deltas behind `expect/actual`; the simulator already proves the storage interfaces are honest. (3) **plugin loading needs a declarative (non-code) tier before ecosystem ships** — DEX-only is Android-only by construction; iOS forbids runtime code load entirely. (4) **NO Android feature regression when iOS lands** — iOS may ship a strict subset, negotiated *down* per session via HELLO `supportedFeatures`, never enforced upward onto Android; reviewer test for every cross-platform change: "does this still work for two Android peers?" If no, reject. (1)+(2) are worth doing regardless of iOS — they also unlock O54/O106 Linux nodes. **Post-merge note (2026-07-16):** the KMP layout was flattened to plain JVM in the merge; `core/platform/` shims + `ios/` bridge spec kept so this decision stays cheap to execute — re-splitting is per-file mechanical. Full per-constraint elaboration + iOS-specific work list archived in `docs/COMPLETED_GAPS.md` (O63 archive). |
| O82 | **`[DECISION]`** Median-clock consensus — NOT a core protocol feature; each use case has a better local fix | The proposal was Bitcoin-style network-adjusted-time at HELLO so code that wanted "a shared clock" could read a median across recent peers. **Rejected on review:** every use case Rumor actually has is better served by a local primitive that doesn't require trusting peer-reported clocks. (a) Relay-deletion-on-ACK (O40) → TTL since `receivedAtMs`; each relay decides locally. (b) Scheduled messages (O22) → fire on sender's own clock; no consensus needed. (c) Room mod-action ordering (O79) → Lamport / vector clocks (per-node monotonic counters), the textbook distributed-systems answer. (d) Anti-replay windows → `receivedAtMs` delta or sequence-number window. (e) "What time is it?" without internet → real UX question but it's a UI/utility need, not protocol; ships as an opt-in plugin or sister app (think mesh-NTP-replacement), never in `:core`. The median-clock approach is sound math chasing a problem that doesn't exist here — and it adds Sybil surface (peers can lie about their clocks to drag the consensus) for no actual win. Row kept as a decision so the temptation to add it recurs against the recorded rationale.  Feeds the O95 ordering decision as an input. **2026-07-24:** re-raised as an *authority-tier-restricted* median for timeout expiry (O152) — the tier restriction genuinely answers this row's sybil objection (authority isn't mintable), but it still fails as a *time source* (partition-inconsistent: partitions see different tier subsets → different medians; plus a per-timeout coordination round). It survives only as a coherence *canary* (detect lost sync, don't derive time) — and even that was dropped when epoch-mode was made a **manual** switch (O152). Net: confirms this row. |
| O86 | **`[DECISION]`** Payments are out of Rumor scope — full stop (user ruling 2026-07-19) | A "mesh crypto" / value rail (Cashu, Lightning, generic) is useful when external infrastructure is degraded, but it is NOT Rumor's job and NOT a companion we build — a DEX or external plugin does this. Rationale: money-transmission regulation (FinCEN MSB / EU MiCA) may attach to whatever "facilitates" transactions, so Rumor stays unambiguously a transport carrier; and conflating identity/messaging/payments into one audit surface is a liability. Rumor exposes only identity + signing + opaque-blob DM + cross-network bridging (O84); anything wanting to carry value builds on that externally, never inside Rumor. |
| O104 | **`[DECISION]`** Post-SHTF hardware realism: owner-unlockable Androids + USB-bootable Linux, everything else is firmware-locked** | Modern devices are mostly too locked down at the firmware level to repurpose. The realistic post-SHTF hardware inventory is exactly two classes: **(1) Android phones still in their owner's possession** — the owner can unlock and sideload, which is Rumor's current target; **(2) Linux-capable laptops/desktops** that can boot Rumor from USB or be reflashed from USB via the boot menu. Everything else (iOS, smart TVs, consoles, locked-bootloader routers, most Chromebooks) is effectively e-waste for mesh purposes — do not design for commandeering it. **Implication for O54:** deprioritize exotic embedded ports; the second form factor should be a **bootable live-USB Linux image** running a Rumor node. Key simplification: `:core` is pure JVM and `:simulator` already proves it runs on desktop Linux — a Linux node is *packaging + transport* work (wpa_supplicant P2P / mDNS-LAN per O93 / USB link), **not a rewrite**. The "port the relay subset to non-JVM" idea in O54 remains only for genuinely constrained targets, if any survive this filter. Refines O55's fixed-infrastructure framing: window-mounted phone + USB-booted laptop on UPS are the anchor form factors. **Analysis (agreed 2026-07-15):** (i) the Linux node should skip wpa_supplicant Wi-Fi Direct entirely — **the laptop should *be* the AP**: hostapd + a Rumor node on its own LAN, phones join as ordinary Wi-Fi clients, mDNS/LAN transport (O93) carries frames. Strictly easier than making Linux speak P2P, and it *solves* O93's STA-coexistence problem for every phone nearby — any USB-booted laptop becomes exactly the fixed-infrastructure anchor O55 wants. (ii) x86 laptops are even more viable than framed: Secure Boot without a BIOS password still usually permits USB boot; the truly locked class is mostly ARM tablets/Chromebooks. |
| O125 | **`[DECISION]`** Extract/generalize unique code + knowledge into standalone artifacts — DEFERRED until post-wire-lock / first release** | Recurring idea (raised 2026-07-18): pull Rumor's distinctive pieces out as reusable libraries. **Deferred, not rejected — and mostly the wrong vehicle.** Rationale: (a) the strict `:core`/`:app`/`:simulator` compartmentalization already IS the extraction that pays off — `:core` is pure JVM behind storage/transport interfaces, and `:simulator` is a permanent *second consumer* that keeps those interfaces honest (the API-review benefit of publishing, for free, without publishing). (b) Publishing artifacts adds semver discipline, API-stability promises, separate CI/repos, and — the load-bearing objection — **freezes wire/API surfaces that are deliberately still fluid** (e.g. the HLC counter went Int→Long "for free" this cycle precisely because the wire is fleet-only; a published lib kills that). Pre-first-release, extraction is paying interest on a loan nobody's taken out. **When the time comes, candidates are NOT equal — ranked:** (1) **`HlcClock`** — small, pure, genuinely generic, pin-attack analysis already written (G42); cleanest extraction. (2) **`Rbsr.kt`** — strongest on paper (no good Kotlin negentropy exists publicly) but Rumor's fingerprint deliberately diverges from the reference (additive-over-hashed-items, because ids are sender-chosen — see O-rbsr-v2 tombstone), so it's NOT NIP-77-compatible; honest extraction means "negentropy-hardened-for-adversarial-ids" (niche) or a pluggable formula (reintroduces the forgeability footgun) — record this tension before anyone extracts it enthusiastically. (3) The **Wi-Fi Direct work** (`PersistencePlanner`/`BackboneRealizer`/`GroupCredentials`) — the valuable artifact is a **writeup, not a library**: the hard-won knowledge is field facts (only autonomous `createGroup` honors the channel; deterministic SSID/PSK gets prompt-free joins; per-OEM quirks) that transfer as documentation far better than as a Maven dep whose hardcoded parts every other mesh will differ in. **Never extract** the crypto shims (`HmacSha256`/`HkdfSha256`) — the world has audited versions. Tiny generic pieces (`CompressedPaddedCodec`, `MultiRecipientEnvelope`) — vendor ~200 lines, extraction overhead exceeds the code. **Knowledge-extraction corollary:** `docs/wire-format.md` (already an O75 precondition for byte-compatible reimplementations) + the field-fact writeups are the better generalization vehicle for most of this project's uniqueness; specs over libraries. **2026-07-24:** the "publish `wire-format.md` as the public, insertable protocol spec" direction (someone can fork the Rumor protocol with their own spin — plugins customize *on-network*, a protocol fork is a *separate* network; no O63 conflict, since O63 governs Rumor's own cross-platform consistency not others' forks) is exactly this row's specs-over-libraries corollary. `wire-format.md` is the vehicle. |
| O146 | **`[DECISION]`** DM vs Room — unify at the envelope + routing-tag layer, NEVER at the membership/concept layer (2026-07-24) | A DM is the N≤2 case of the room envelope, not a room. **Share bottom-up:** the `MultiRecipientEnvelope` codec (a DM = N={me,them} wraps) and the HMAC routing-tag matcher (O53 sealed-sender tag ≡ O79 `RoomRoutingTag` — same mechanism). **Never share the concept:** a room's defining machinery — the authored signed membership op-log (O79), posting certs (O89), channels, moderation — is exactly what a DM has none of; modeling a DM *as* a room either wastes ~90% of room features or (the trap) drags a pairwise chat through the op-log state machine. A room is *created* (RoomCreate + roomId); a DM just exists (deterministic pairwise id, no ceremony). **FS landmine:** DMs have O38 receiver-FS (rotating prekeys); the room envelope is sender-FS-only — any shared wrap MUST carry prekey selection into the wrap step or DMs regress to the Briar-BHP hole. Keep `DIRECT` and `ROOM_MESSAGE` distinct MessageTypes; share the envelope + tag as libraries both compose paths call. All within the RumorMessage content layer — not an O65 two-wire-layer violation. Cross-refs O79, O53, O38, O65, O89, O147, O155. |
| O147 | **`[DECISION]`** Membership is one spectrum by governance — fixed/derivable vs governed/mutable; DM/group-DM/small-room are one primitive (2026-07-24) | The DM-vs-Room line is drawn in the wrong place. The real axis is **membership governance**: (1) **fixed/derivable membership** — no op-log, no creation ceremony, deterministic id from the member set, full prekey FS; a DM is the N=2 point, and small private group chats belong here too (today homeless). Membership *changes* by **fork** (add/remove = a new fixed set everyone migrates to — no authorization consensus, no enforcement problem, better FS for free). (2) **governed/mutable membership** — op-log, ranked authority (O148), certs, moderation. The ONE thing that necessitates the heavy governed structure is **enforced-authority-at-scale**: fork can't re-invite 500 people per change, and fork *abandons* a removed member rather than *revoking* them (useless for kicking a spammer). So governance machinery exists only for that tier; everything else is fixed-membership-with-fork and strictly simpler. Full derivation in `docs/MODERATION_AUTHORITY_RESEARCH.md` §0/§11. Cross-refs O146, O79, O38, O135, O155. |
| O150 | **`[DECISION]`** Room owner-gone → headless by default; succession never inferred from silence (2026-07-24) | An async network cannot distinguish "owner temporarily partitioned" from "owner gone forever" (failure-detector / FLP impossibility), so NEVER auto-promote/succeed on owner-absence — it split-brains on heal. **Default: headless** — the ranked hierarchy (O148) keeps running, joining keeps flowing, ordinary moderation continues; owner absence only removes the ability to mint *new top-tier* authority, rarely needed (cf. Discord servers running fine on admins under a dead owner account). **Entry policy and governance policy are independent** — for a social space the owner isn't in the join path, so "freeze membership on owner-gone" was the wrong instinct. Succession, when wanted, is an **explicit named list** in the signed RoomCreate (a *separate* list from rank — honors "trusted as admin, not as owner"), activated ONLY by the owner's own signed O69 `IDENTITY_RETIRED` (an unambiguous positive event, never an inference). Optional top-tier quorum, also O69-gated. **No elections/voting** — one-key-one-vote is sybil-farmable on free identities (the sole literature *contradiction*, Aether; `MODERATION_AUTHORITY_RESEARCH.md` §4); use invite-provenance (O151), not plebiscite. Cross-refs O69, O148, O151, O135. |
| O155 | **`[DECISION-LEAN]`** Encryption is baseline for every bounded-membership surface; the feed is the sole plaintext surface; OPEN-*room* mode dissolves (user direction 2026-07-24) | User intuition, adopted as direction: encrypt everywhere by default. It gets *cleaner* under "no public rooms" (O154): every bounded-membership surface — DM (N=2), group chat, invite room (any N) — has a known member set, so all are **ENCRYPTED, always, no per-room toggle** (a toggle only adds downgrade-attack surface + misconfig; the real "toggle" is the surface choice — post to a bounded room [encrypted] vs the public feed [plaintext]). **The OPEN unencrypted *room* mode dissolves** — it existed only to serve public/large rooms cheaply, which no longer exist; its wire mechanism is retained AS the feed transport (O154). **The feed is the one principled plaintext exception, and that is honest not weak:** a broadcast to an open unbounded subscriber set *cannot* be confidential (the "key" is effectively public) — plaintext-but-Ed25519-signed is correct; confidentiality of a public post is a contradiction. **Open question (why this is LEAN not final):** the cheap/confidential/large **tradeoff triangle — pick two.** Encryption-baseline picks *confidential*, so a large *invite* room pays the O79 O(N)-wraps envelope (~48 B × N/msg — brutal past a few thousand). If large encrypted rooms are a real target, revisit the efficient-group-key options O79 deliberately dropped (MLS/TreeKEM log(N) rekey, sender-keys — `MODERATION_AUTHORITY_RESEARCH.md` §6) vs. accepting that very-large communities are feed-shaped (O154) and thus not confidential. Resolve before ratifying. Cross-refs O79 (two-mode split revised), O146/O147 (DM/group = encrypted envelope), O154 (feed = plaintext), O38 (DM FS), O36. |

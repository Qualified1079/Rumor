# O229

**`[STRUCT]` `[TODO/CODE]`** `MeshRuntime` has no lifecycle state — its loops outlive `stop()` (filed 2026-11-06, implicit-state-machine audit; verified)

`MeshRuntime.stop()` (`core/runtime/MeshRuntime.kt:247`) only nulls `coordinator`/`debouncedHlc` and says "loops die with the host scope", but `MeshService` passes its service-lifetime `scope` (`MeshService.kt:118`), which `stopMesh()` (:373) never cancels.
After stop, the beacon loop keeps composing SELF_PRESENCE with empty neighbors, the backbone recompute loop keeps calling `applyBackboneRole` on a stopped `WifiDirectTransport`, and the `incomingMessages` collector stays live.
A second `startMesh` in the same process would double every loop and the plugin sink — the §5 double-delivery bug `meshStarted` exists to prevent. Also:
`start()` has no double-start guard (a pending HLC value in the replaced store is lost); `hlc.onAdvance` / `presencePulse` hooks are never cleared.
Latent today because `stopMesh` only runs from `onDestroy`. **Fix:** `start()` creates and owns a child `Job`; `stop()` cancels it;
an explicit `Idle/Running/Stopped` state rejects double start.
Same shape for `MeshService`'s own collectors at :238–:290 (also launched into the service scope and not cancelled by `stopMesh`).
`:node` (`Main.kt:186`) cancels its scope and is fine. Bundle with the `DebouncedHlcStore` half of this row:
if its scope dies while `scheduled=true`, every later `save` only updates memory, silently and permanently (:54);
and the timer and `flushNow` both write outside the lock, so the clean-stop value can be overwritten by an older one (restore max-merges, so it is safe but defeats O130(e)).

# O167

**`[TODO/CODE]`** `LanTransportManager` `NetworkCallback` not pinned to the `Network` it started with (filed 2026-07-30, audit #20)

`app/.../transport/lan/LanTransportManager.kt` `start()` registers a callback for `addTransportType(TRANSPORT_WIFI)` — matching ANY Wi-Fi-transport network.
`onLost(network)` tears down the transport on loss of any matching network without checking it's the same `Network` object `onLinkPropertiesChanged` used to bring it up.
If the device briefly has two WIFI-transport networks (a captive-portal validation network, or on some Android versions a P2P group interface also classified under `TRANSPORT_WIFI`), a spurious loss of the unrelated one incorrectly tears down a good LAN transport.
Fix: capture the started `Network` and check `network == startedNetwork` in both callbacks. Cross-ref O93, O107.
**Same component, more implicit state (2026-11-06 audit, reader-reported):** a DHCP renew to a new address is ignored by the `transport != null` guard (:49);
`stop()` on main races a ConnectivityThread callback already past :49, which can start a transport and hold the multicast lock after teardown;
a throwing `t.start(addr)` leaves `transport` non-null so every later callback returns early;
there is no `onTransportDown`, so MeshService's `lanCollectJob` (written from the ConnectivityThread, read on main) keeps collecting a stopped transport.
Fix all with an explicit `Stopped/Watching/Up(network, address)` state.

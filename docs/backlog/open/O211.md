# O211

**`[DECISION+TODO/CODE]`** Toolchain modernization — Kotlin 2.x first, then JDK 21 for the pure-JVM modules (filed 2026-10-10, user question)

**Position:
yes, move — but not JDK-first, and not all four modules together.** Today every module pins `jvmToolchain(17)` + `VERSION_17` (AGP 8.13.2, Kotlin 1.9.22).
The 17 pin is *required* only for `:app`; `:core`/`:simulator`/`:node` are plain JVM and inherit it by habit.
**Why move at all (project-level, not convenience):** O55's horizon is decades of infrastructure-down operation and `:node` is the artifact meant to run for years on USB-booted laptops (O104/O106) — shipping it on an LTS with a shorter remaining security-patch stream is a liability for a security-critical app, and patches are the point under that model.
Virtual threads (Loom, 21) also genuinely fit `:node`'s workload: the "laptop IS the AP" anchor is many concurrent sockets serving nearby phones.
Coroutines already cover this, so the gain is real but not dramatic.
**Why NOT JDK-first:** for a Kotlin codebase the JVM number buys almost nothing (Java language features are irrelevant here) — the actual modernity win is **Kotlin 1.9.22 → 2.x (K2)**, which is also where the compile-speed and tooling gains are.
JDK 21 on Kotlin 1.9.22 is the less valuable half. A split toolchain is a real cost too:
two JDKs in CI, contributors needing both, and `:app` cannot follow until Android's timeline permits. **Sequence (the load-bearing part of this row):
(1) O208 — get CI reporting a verdict again, because a toolchain change with nothing verifying it is how a silent breakage surfaces three sessions later;
(2) Kotlin 1.9.22 → 2.x; (3) `:core`/`:simulator`/`:node` → 21, `:node` leading (strongest case, smallest blast radius, no Android and no F-Droid exposure);
(4) `:app` on Android's schedule, never ahead of AGP's supported build JDK.** Doing (3) before (1) is the one ordering to actively refuse.
**Scope note:** F-Droid reproducibility (O49, `docs/FDROID_BUILD.md`) touches **only `:app`**, so moving the JVM-only modules does not invalidate the build recipe — an earlier session's objection on this point was wrong and is corrected here.
Cross-refs O208 (CI gate), O106/O104 (`:node` horizon), O49/O56 (ship constraints, `:app` only).

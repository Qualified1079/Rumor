O55/O26: no app store post-collapse. **Primary vector is SNEAKERNET (user clarification 2026-07-22):
USB drives, SD cards, phone-to-phone APK copy — because ~99% of phones won't be running Rumor, so first-spread is physical media, not the mesh.** A malicious actor hands out a backdoored build (exfiltrates keys, weakens crypto, disables the O135 sybil defenses, logs the social graph).
No CA to verify against.
**Sneakernet actually FITS the web-of-trust model well** — you got the APK from a specific person you can name and attribute, so a signed "I built/verified this, hash H" that travels *with* the drive, checkable against a pre-distributed project fingerprint, is exactly the right shape (physical provenance = the attack edge is a real person you can vouch-for or block).
**Layered answer (most already-free → hardest):** (1) **Android APK signature continuity is already the strongest built-in defense and it's FREE** — an update APK must be signed by the same key as the installed app or Android rejects the install.
So a malicious build **cannot update a genuine install** (different key → rejected).
The attack surface is therefore *only first-install/bootstrap*, not updates.
Verify the release keystore (`app/keystore.properties`) is treated as the continuity anchor and documented as such.
(2) **Bundle the project release public key INTO the app** so a genuine copy can verify the *next* build's signed hash forward (chain of trust from any known-good copy) — pairs with `docs/PROJECT_KEYS.md` (key not yet generated) and O50's N-of-M maintainer co-signing extended from plugins to the core APK.
(3) **Reproducible builds (O49, extend from plugins to the app)** — public source + deterministic build = anyone technical rebuilds and confirms `SHA-256(APK)` matches, without trusting the distributor;
the foundation that makes attestation meaningful.
(4) **Community attestation of the APK hash (O26, extend to the app)** — the build hash accumulates signed "I rebuilt from source, hash matches" attestations;
accept a build attested by people in YOUR trust graph (ties directly to O135 web-of-trust — same vouch primitive, applied to the binary).
(5) **OOB/physical key-fingerprint distribution** — the project key's O21-style memorable fingerprint on paper / painted at a community hub / on a trusted USB, so first-install can be checked against a known-good root obtained off-mesh.
**Irreducible residual (honest-docs, O27-style):** the "trusting trust" / first-copy-from-a-fooled-trusted-person case has NO pure-crypto fix — mitigated by reproducibility + diverse independent attestation + trust-graph vouching, never eliminated.
Say so plainly. **Cheapest first:
document the APK-signature-continuity property + generate the project release key (PROJECT_KEYS.md) + bundle its pubkey.** Cross-refs O26/O49/O50 (plugin-scoped versions of 2/3/4), O55 (mesh-as-distribution), O135 (web-of-trust vouch primitive reused for binaries), O21 (fingerprint), O27 (honest limits).

# O140

**`[TODO/CODE+DECISION]`** Unified "subscribe to a signed feed" primitive — one mechanism under many features (filed 2026-07-22, user insight)

User observation:
the same subscribe-to-a-signed-append-only-feed primitive already underlies, or should underlie, a whole family of features — **blocklists** (O67/O78, exists), **keyword-filter lists** (O67, exists), **site/page updates** (O101 — subscribe to a site's signed diff feed), and **person-follow** (which **auto-relay already IS** — auto-relaying a peer = subscribing to that person's output;
this also becomes the O135(4) vouch/hops "follow"). Rather than build each subscription silo separately, recognize the shared shape:
*a signed author + an append-only stream + a local opt-in to replicate/apply it + granular layering of multiple subscriptions.* The O67/O78 sign/verify/publish/subscribe machinery is the substrate to generalize.
**Hard invariant that stays true across ALL of these (user reminder 2026-07-22):
a block NEVER blocks a relay** — subscriptions/blocks/filters are display-and-apply-layer only;
the node relays everything regardless (the relay-never-touches-blocklist invariant, see Design Decisions).
A subscription changes what YOU see/apply, never what the mesh carries.
**Deliverable:** a design pass that factors the common subscription primitive (author-signed feed + subscribe + layer + apply-locally) so sites (O101), follows (auto-relay → O135), filters (O67), and blocklists (O78) are instances of one mechanism, not four codebases.
Cross-refs O67, O78, O101, O135(4) (follow=subscribe-to-person), O36 (append-only signed broadcasts are the primitive), auto-relay (the existing person-subscription).
**2026-07-24 additions to the instance list:** **room-message consumption** (an OPEN room / feed IS a signed broadcast feed to a routing tag — consuming it = the subscribe primitive;
user insight) and **global-feed shards** (O154 — each named global is just another feed tag you subscribe/switch to). Both fold into the same mechanism.

# O80

**`[PART]`** User-customisable mode-transition schedule

Core data model + matcher shipped:
`core/mode/ModeProfile.kt` carries an ordered `List<Rule>` where each Rule is `(Condition, targetMode, optional per-rule overrides)`.
Conditions cover battery-above/below threshold, charging state, screen on/off, network (Wi-Fi/cellular/offline), time-of-day range (wraps across midnight), weekday set, and AND-composition.
`ModeProfile.evaluate(state)` returns the first matching rule's target mode or the default. `ModeProfileTest` covers each condition + a realistic profile.
**Orchestrator + hysteresis + pulses + transition log + starter template all shipped — see G39** (`AutoModeController`, `ModeOrchestrator`, 4-way Settings selector).
**Remaining here:** the rule-editor UI (compose/edit/reorder rules), profile persistence (today the profile is the hardcoded `AutoModeController.starterProfile()` — nothing to persist until users can edit), and applying per-rule overrides (`scanIntervalMs`/`gossipCadenceMs`/`maxSessionMs`) on top of the active mode's envelope.
Cross-references O33 (battery measurements help users pick threshold values), O62 (single source of truth for mode behaviour), G39.

# O191

**`[TODO/SIM]` — NOT committed; de-risk in the simulator first** Ratcheted DM path — Double Ratchet for 2-person DMs; would supersede O38, absorb O53 + repudiable-auth (filed 2026-07-30, privacy workshop)

**Status: this is a candidate, not a decision.
There appear to be real issues (the four mesh-hard points + the wire fork below) — prototype the idea in the simulator and measure it before committing to build it for real.** What the sim must answer before we say yes:
does the ratchet survive mesh conditions (out-of-order + gossip-duplicated + week-delayed + never-answered delivery) without unacceptable message loss;
what MAX_SKIP cap balances legit multipath gaps vs the skipped-key DoS; and does the wire fork (below) actually hold up against relay dedup + verification.
Only after the sim de-risks it does this graduate to a design doc + code. DMs are effectively 2-person rooms → adopt Signal's Double Ratchet.
**Unifies four things into ONE DM-path redesign:** per-message forward secrecy (strictly better than O38's coarse hourly prekey rotation), post-compromise/self-healing security (O38 gives NONE), sealed-sender/tag addressing (= O53), and **repudiable authentication** (the ratchet's per-message MACs mean either party could forge → no third-party proof;
this is the standalone "#2 deniable DMs" idea, free from the ratchet). Rooms/broadcasts UNTOUCHED — they keep signed multi-recipient envelopes (O79);
only 2-person DMs ratchet (as Signal uses pairwise ratchet for 1:1, Sender Keys for groups).
**Maps cleanly to Signal, no special handling:** out-of-order + gossip duplication (header `(ratchet-pub, PN, N)` selects the right message key;
the existing RumorMessage-id dedup layer sits ABOVE the ratchet, drops repeats before decrypt);
stalled DH ratchet on slow/never replies (Signal also doesn't advance DH until a reply — you keep per-message FS throughout, just no PCS refresh;
on mesh you live there longer, degrading gracefully to a pure symmetric hash ratchet — still strictly > O38).
**Genuinely mesh-hard (design around):** (1) **skipped-key DoS** — a message claiming N=1e6 asks for 1e6 derived keys;
needs Signal's MAX_SKIP cap, tuned higher for mesh multipath but hard-bounded (too low loses legit delayed msgs, too high = DoS; sim it);
(2) **X3DH without a server AND without one-time prekeys** — O38's PREKEY_PUBLISH gossip IS the signed prekey (async, no server);
drop one-time prekeys (gossip has no clean consume-exactly-one), accepting a first-message FS-slice + replayability, bounded by O38's hourly signed-prekey rotation;
(3) **ratchet-state vs ephemeral collision (O190)** — state must survive restart for a session to continue; resolution:
ephemeral mode resets ratchets → re-run X3DH; skipped-keys-for-undelivered are a small standing FS liability;
(4) **THE ONE WITH TEETH — sender-hidden DMs break O16 per-sender rate limiting** — a ratcheted/sealed DM is an opaque tagged blob the relay can't attribute to a sender (the point), so per-sender limiting on DMs is impossible → fall back to per-link / per-recipient-tag limiting (conscious spam-control downgrade traded for unlinkability, not a surprise).
**Two USER threat-model calls to ratify before build:** (a) accept X3DH-without-one-time-prekeys (first-message replay window);
(b) accept per-link rate limiting on DMs in exchange for unlinkability. Both provisionally YES. Own design doc before any code;
verify it doesn't break the O65 two-wire model / relay dedup / verification — DMs stop being signed RumorMessages, become tagged AE payloads (a real but coherent fork).

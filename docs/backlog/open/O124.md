`GossipEngine.presencePulse` host hook + `PresenceReplyGate` (responder-clock per-peer cooldown 30s (was 2 min, user-tuned), LRU-bounded, replies only for unknown-or-stale peers via `MeshViewTracker.hasFresh`) wired in MeshService;

**Remaining:** LAN/mDNS re-query on the button (LanTransportManager has no cheap requery — transport rounds poll anyway), O97 status surface. Original design:
Field-observed:
the search-for-peers button doesn't refresh mesh-level visibility — a node invisible for lack of a first exchange (see O97 field note) stays invisible after tapping it.
Design:
button = (a) transport refresh (BLE scan/advertise restart, P2P discovery kick, LAN mDNS re-query — cheap, local) **plus** (b) an immediate SELF_PRESENCE pulse (the O30/G12 entry-pulse primitive, fired on demand) so the next exchange carries our announcement;
and (c) **solicited response**:
a peer receiving a fresh pulse from an unknown-or-stale peer replies with its own pulse, gated by a **responder-side per-peer cooldown** (local clock, e.g.
≥N min since last pulse to that peer) so a modified client spamming probes cannot force pingspam — the cooldown is enforced by the responder, not trusted from the wire (user-specified anti-abuse shape).
No new message type: reuse SELF_PRESENCE; the "solicit" is implicit in receiving a pulse from someone whose beacon we haven't answered lately.
Cross-refs O30 (pulse primitive), O97 (status surface showing "announced/pending"), O16 (rate-limit family).

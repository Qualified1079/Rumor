# O187

**`[PART]`** Room lifecycle — wire transport + RoomRepository + authority + Android persistence SHIPPED; UI open (2026-10-10; persistence 2026-11-08)

**Shipped (verified, `:core` 488/0 + `:simulator` 136/0):** three new MessageTypes (`ROOM_CREATE`/`ROOM_INVITE`/`ROOM_ACTION`, serial names reserved in `RENAMED_FIELDS_NEVER_REUSE.md`, INFRASTRUCTURE class, relayed broadcast-style so a roster change reaches members who were offline);
`core/data/RoomRepository.kt` + `RoomRecord` (policies, mods, members, bans as explicit relations — the flat shape O148/O149 refine, not a guess at their model) + `InMemoryRoomRepository`;
`RoomAuthorityResolver` — **the first real implementation of O89's `RoomAuthorityProvider`, which until now had none, so governed rooms could not exist**;
`composeRoomCreate`/`composeRoomInvite`/`composeRoomAction`; receive-side `handleRoomLifecycle`. **Invariant worth not breaking:
the carrying message's sender must BE the inner author.** Relay preserves `senderId`/`senderPublicKey` and ingest already proved `senderId == SHA-256(pubkey)`, so that one rule gives every hop the right key to verify the inner signature without a contact lookup, and stops a third party re-wrapping someone else's room decision.
**roomId is DERIVED, not asserted** (`RoomId.derive(creatorId, nonce)`, signed via the `rumor-room-create-v3:` transcript):
the first cut let a creator assert any roomId and resolved collisions first-writer-wins, which — since a roomId is public, the routing tag being a keyless hash of it — made room ownership a squatting race whose winner differed per node.
Derivation removes the race instead of arbitrating it:
a CREATE must be signed by `createdBy` AND carried by that sender, so no one can produce a CREATE for an id deriving from someone else's identity.
**Caught by automated security review, HIGH** — and it matched the codebase's own grain (userId = SHA-256(pubkey), trafficClass derived not asserted), which is the tell it should have been derived from the start.
Other decisions pinned by tests: a **ban outranks a later invite**;
the creator's own moderator status is **not removable** (else an emptied mod list leaves the room permanently ungovernable);
**a ban is checked ahead of every other posting gate** (a banned user may still hold a cert issued before the ban);
**membership is enforced for every room with a roster** — the first cut returned early for non-MOD_APPROVED rooms with a comment claiming membership enforced it and nothing did, so MEMBER_ONLY rooms had NO write enforcement at all (also caught by review).
`RoomLifecycleTest` (8) + `RoomPostingAuthorityTest` (10) drive a real second engine via `onExchange`;
every guard is caught by exactly one test under teeth-check, including the three added from the security review (derivation, ban-ahead-of-cert, membership).

**`[STRUCT]` `[PART]`** `:node` module — headless JVM runtime shared by desktop app and USB-bootable service**

**Headless test node SHIPPED 2026-07-22** (`docs/NODE_KICKOFF.md` both steps done):
(a)-extraction landed as `core/runtime/MeshRuntime.kt` (host-agnostic orchestration — reseed, purges, coordinator + beacon/recompute loops, HLC persistence via `HlcStore` port, incoming-sink + backbone-realizer lambdas;
MeshService now hosts it, byte-identical behavior, all suites green) and `:node` (4th Gradle module) runs the real engine over the G40 `LanTransport` with the in-memory repos (moved `:simulator/data/InMemoryRepos.kt` → `core/data/memory/`), file-backed identity+HLC (`~/.rumor-node`, unencrypted — TEST INSTRUMENT, the product node gets the O44 encrypted impl), and a localhost status page (JDK HttpServer, zero deps:
peers/messages/events + send box; also curl-able for scripted driving). Verified:
two nodes on one machine mDNS-discover, complete signed HELLO + gossip sessions, deliver an HTTP-composed broadcast end-to-end to overlap=1.0. Run:
`./gradlew :node:installDist && node/build/install/node/bin/node [--bind ip] [--http port] [--data dir]`.
**Remaining here = the product node** (2026-07-19 decision: waits until the phone is finished): The load-bearing decision (`:
core` pure JVM, proven headless by `:simulator` for months) means most of the work is *assembly*, not porting. Pieces, each with an existing seam:
(a) **`MeshRuntime` extraction** — the wiring in `MeshService.startMesh()` (engine ↔ transport config, reseed, flow collectors) is Android-hosted but not Android-shaped;
extract to `:core` so MeshService, a desktop `main()`, and a systemd unit each just host it.
(b) **Storage** — repos are already interfaces with Room + in-memory impls; :node needs a third:
SQLDelight (one impl everywhere) vs JDBC-SQLite adapter (less work) — see re-scored O1; decide when this row starts.
(c) **Identity** — file-based encrypted impl behind the existing `IdentityProvider` interface (see O44 platform-fork note).
(d) **UI — GUI-first, never headless-facing (user correction 2026-07-15):** the median person in an austere scenario must be able to set this up, so the USB image boots *straight into* a dead-simple fullscreen GUI — big status ("Rumor running", peer count, network name), on/off, zero config, identity auto-created on first boot, AP auto-started;
a terminal must never be visible.
The *runtime* stays UI-agnostic (that's the :node/MeshRuntime split), but "headless daemon you ssh into" is not a product surface. Two implementation paths:
kiosk-browser fullscreen on the localhost Ktor dashboard (cheapest, steals the `:simulator` pattern;
localhost violates no offline/no-CDN rules) or a small dedicated Compose Desktop status app (a purpose-built ~3-screen UI — NOT a CMP migration of `:app`, which stays off the table until real demand).
(e) **USB-boot packaging** (ops, not architecture):
persistence partition on the stick — identity + message store MUST survive reboot (fresh identity per boot = broken); hostapd laptop-as-AP config per O104;
autostart straight into the GUI. **Archimedes' O83 (desktop macOS/Linux/Windows relay-node targets) folded here** — same deliverable;
macOS note from O104 discussion: Macs are a :node packaging target, not a reflash target (Apple Silicon can't live-USB boot;
any Mac that boots macOS runs the JVM node natively).

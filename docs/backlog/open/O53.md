**`[PART]`** Sealed-sender DMs — recipient-derivable delivery tag** — **crypto primitives + compose-side stamp shipped;
receiver-side precompute + relay routing open.** `core/crypto/HmacSha256.kt` — pure-Kotlin HMAC-SHA-256 over the existing `Sha256` shim (no new platform actual;
RFC 4231 vectors 1, 2, and the oversize-key path pinned in `HmacSha256Test`).
`core/protocol/SealedSenderTag.kt` — `tagFor(sharedKey, messageId)` returns the 32-byte HMAC over `"rumor-dm-v1:" || messageId`.
`core/protocol/SealedSenderKey.kt` — `derive(myUserId, myEd25519Priv, theirUserId, theirEd25519Pub)` returns the per-contact 32-byte HKDF key from X25519 ECDH of the Ed25519-derived static keys;
userIds sorted into the HKDF info so direction doesn't matter. `core/wire/SealedSenderTagExt.kt` — `_ext.t` accessor + `withSealedSenderTag` helper.
**Compose-side wired (this session):** `GossipEngine.composeDirect` derives the per-contact tag key, computes `SealedSenderTag.tagFor(tagKey, msg.id)`, stamps `_ext.t = base64(tag)`, zeros the tagKey in finally.
Skipped for bridged DMs (recipient is foreign-network, not Rumor Ed25519). `_ext` is excluded from `signableBytes` so the outer Ed25519 sig stays valid.
Simulator pin:
`SealedSenderTagWireTest` (2 tests) drives a real `composeDirect` and proves the recipient (independently deriving the per-contact key) computes a matching tag for the same messageId — the property a relay's pre-match table will exploit.
Different recipients on the same sender stamp different tags. Domain tags `rumor-dm-v1:` (tag) and `rumor-dm-recipient-tag-v1:` (key HKDF) reserved forever.
**Not done:** receiver-side precompute store (per-contact `tagKey` cached at contact-load time, refreshed on contact-add/remove);
relay routing path matches inbound `_ext.t` against the precomputed set instead of routing on plaintext `recipientId`;
eventual wire-format-break to remove plaintext `recipientId` once the tag path is universally deployed. The remaining work is on the receive/routing layers;
both substrate and compose-side are now bounded and tested. Original spec retained for the open work: Generalization of O52's broadcast tag to all DMs.
Replace plaintext `recipientId` field with `T = HMAC(K_recipient, "rumor-dm-v1:" || messageId)`.
Relays match incoming DMs against the small set of `T`s they've precomputed for keys they hold; non-recipients can't link DMs to recipientIds on the wire.
Signal calls this "sealed sender"; their version trial-decrypts which is expensive — the tag pattern gives the same property cheaply.
Closes the plaintext-recipientId leak on every DM (currently the dominant on-wire metadata leak);
pairs with O29 breadcrumb routing — breadcrumb signals (recent-inbound-peer, ACK return path) work on tags too once the local node has computed them per-contact.
Wire-format change: add tag field via O37's `_ext` until protocolVersion bump. Ported in the merge.

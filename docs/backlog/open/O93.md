Cross-ref O124 (search-button manual refresh is the on-demand cousin). **STA↔P2P coexistence — is churning the only fix?
(user Q 2026-07-22, live-confirmed partition):** disconnecting a single-radio phone from the AP partitions it (LAN dead → falls back to Wi-Fi Direct;
the LAN group can't reach it). Three fixes, best-first, churn is the *fallback* not the answer:
**(A) same-channel STA+P2P concurrency** — force the P2P group to the *current STA channel* (the O98 channel-honoring `createGroup` path);
most chipsets run STA + one P2P group concurrently on a *single* channel, so the phone is genuinely on BOTH LAN and Wi-Fi Direct at once and bridges them (GossipEngine relays across transports for free).
This is the real fix; it's device-dependent and needs a per-chipset capability probe.
**(B) infrastructure AP (O104)** — a wall-powered node runs an AP so everyone associates to *it* (all-LAN, no P2P needed at all);
the austere-scenario answer, sidesteps the whole conflict. **(C) churn / DTN data-mule (fallback)** — time-slice:
be on LAN for a window, sync, switch to P2P, sync, carry messages between the two.
Rumor is delay-tolerant (O55) so this is *acceptable*, but it adds latency + connection thrash and should be the last resort when (A) fails and no (B) exists.
**So: probe for same-channel concurrency first (A); deploy infra APs where possible (B);
churn only when neither works (C).** **WIDE-AREA CORRECTION (user 2026-07-22):
(A) only solves the LAN-EDGE bridge (one hop, AP↔P2P) — it does NOT solve a wide-area mesh.** Same-channel STA+P2P lets a node be on the AP + one P2P group at once, but a mesh spread over a large area needs to chain *multiple* P2P hops (node C reaches distant D via its own group while C is a client toward the LAN), and a single-radio phone can be in only ONE P2P group at a time (GO *or* client, not both, not two groups).
So for wide-area the options are:
**(D) GO+client (multi-group) concurrency** — some chipsets can be GO of one group AND client of another simultaneously (the harder cousin of STA+P2P);
this is the non-churn wide-area answer and is exactly the unfinished O98 "multi-group backbone decomposition" work — device-dependent, needs a capability probe;
**LoRa / transport-plugin tier (O54/S1) for genuinely long hops** — Wi-Fi Direct is the wrong radio for miles;
the right architecture is Wi-Fi-Direct clusters stitched by LoRa bridges, not one Wi-Fi-Direct chain spanning the whole area;
**(C) smart churn as the fallback** (user refinement — make it less bad, since sometimes it's unavoidable):
pick mules by **screen-off first** (an idle node's downtime doesn't hurt anyone's active use) and **rotate mule duty** across eligible nodes to minimize per-user downtime — a fairness/scheduling layer on the data-mule model, not blind time-slicing.
Cross-refs O98 (multi-group backbone = option D), O54/S1 (LoRa long-hop tier), O104 (laptop-as-AP = option B), O107 (transports already bridge at the engine layer).
**File the smart-churn scheduler (screen-off-priority + rotation) as its own follow-up when the mule tier is built.** **PRIORITY ORDER (user 2026-07-22, for the wide-area/coexistence case):
(D) GO+client multi-group concurrency is the BASELINE (default attempt) → LoRa if the hardware is present → (C) smart churn as fallback.** (A same-channel STA+P2P and B infra-AP remain the LAN-edge / infra-available cases;
this D→LoRa→C order is specifically the wide-area multi-hop priority.) **Also owed:
both SMART (automatic) switching AND MANUAL (user-override) switching between transports/roles must be figured out** — the automatic policy decides D-vs-LoRa-vs-C and who mules;
the manual surface lets a user force a role/transport (pairs with O97's manual persistent-link control surface).
Make both first-class, not just the auto policy. Original analysis:
With both test phones associated to the same 5GHz AP, `discoverPeers()` succeeded but never produced a PEERS_CHANGED with results — on both a Motorola/Qualcomm and a OnePlus device.
Disconnecting from the AP (radio still on) made discovery return the peer within ~3s.
Users will not drop home Wi-Fi to use a mesh app, so this needs a real answer:
when both devices are on the *same* LAN, mDNS transport (O73-style) sidesteps the radio conflict entirely and is the natural fix;
different-LAN/no-LAN coexistence needs deeper work (listen-channel pinning, discovery-while-associated quirk table, or accepting BLE-only rendezvous with direct-connect).
Also note the system Location toggle (`location_mode`) must be ON for P2P scan results on API 34 devices regardless of NEARBY_WIFI_DEVICES grant — surface a UI warning when it's off.
**Field-confirmed (2026-07-13, 3-device run):** forming the P2P group doesn't just fail-to-discover while STA-associated — it *actively disrupts* nearby Wi-Fi.
The OnePlus GO created the group on 5 GHz ch 36 (`mP2pFreq=5180`); a bystander's 5 GHz Wi-Fi dropped.
On single-radio phones STA + P2P-GO on *different* channels can't coexist, so the OS tears down/moves STA. Two mitigations, both pointing the same way:
(a) **primary fix for casual/home use — mDNS/NSD transport over the shared LAN (O73-style):
when peers are already on the same Wi-Fi, never form a P2P group at all**, which sidesteps both the discovery failure and the interference;
(b) force the GO to the *current STA channel* so STA+P2P run concurrently on one channel (most chipsets support same-channel concurrency;
cross-channel is what forces the disruptive switch). Framing per O55:
Wi-Fi Direct is the *infrastructure-down* transport (no AP to interfere with — the actual design target); mDNS is the *casual-use-on-existing-Wi-Fi* transport.
Both should exist, selected by whether a usable shared LAN is present.

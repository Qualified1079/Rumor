# O204

**`[DECISION + sim-DONE 2026-08-03]`** `hopsToLive` does not bound DM/broadcast reach — store-backfill re-offers as-received copies

**Finding (`SmartRoutingReachTest`, faithful real-offer-path harness):** a flooded DM reaches the entire dedup-bounded connected component, not the 15-hop `hopsToLive` horizon.
`MessageStore.ingest` stores a message at its *as-received* `hopsToLive`, and the durable `offerable` backfill (re-offered every exchange by `messagesForExchange`, filtered only by `hopsToLive>0`) keeps re-offering that stored copy;
the per-hop decrement lives only on the one-shot scheduler relay copy, which the backfill overrides.
So `hopsToLive`/O32's `floodedHops` shape the *ephemeral relay copy* but NOT durable reach. **Disposition:
ACCEPT for now.** For delivery this is a feature (store-and-forward robustness under O55).
For O27/O58 it means a DM/broadcast is seen by every node in the component — but (a) that's already O27's stated property, and (b) O160's breadcrumb **targeting** (validated same test:
routed DM touched 10/26 nodes vs flood 26/26) is the mitigation for DMs that have a crumb trail.
**If bounding broadcast reach ever becomes necessary** (very large single component, privacy), the lever is to persist the decremented value (decrement the stored copy on relay, or have `offerable` re-derive an effective TTL from a real hop count) — but that directly fights delivery robustness, so it needs a demonstrated need first.
Cross-ref O27, O58, O160, O32, O23, O55.

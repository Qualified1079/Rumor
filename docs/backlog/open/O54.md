**`[TODO/CODE]`** Transport plugin tier — non-phone infrastructure**

The existing plugin model (Meshtastic, MeshCore) generalizes naturally to "any device that carries Rumor bytes between two endpoints" — routers, single-board computers, packet-radio modems, satellite modems, USB-CDC links between two stationary nodes.
Two integration paths compose:
(1) **TransportPlugin on the phone** — an Android plugin that speaks to an external device over USB/BLE/TCP and shuttles Rumor frames in both directions, no protocol translation.
The device runs a small daemon (Go/C/Rust binary, OpenWrt package, or systemd service) speaking the Rumor wire format.
Useful for "plug a USB-ethernet adapter from my phone to my OpenWrt router" or "phone-to-Raspberry-Pi over USB serial." (2) **Native relay node** — port the relay subset of `:core` (signature verify, dedup, relay decision, no UI/storage of plaintext) to a non-JVM language for direct deployment on routers, SBCs, or LoRa gateways.
Pre-existing infrastructure (window-mounted SBC on solar, OpenWrt router on UPS, ham-radio packet gateway) becomes a permanent mesh node.
Distinguished from BridgePlugin because there's no foreign network — it's still Rumor end-to-end, just over different physical media.
Plugin capability declaration: `transport-extend` (read+write frames) is APK-tier in O24 because it touches the wire path.
**Threat-model fit:** matches O55's long-term-collapse framing better than crowd-density mesh — fixed-position infrastructure on intermittent power is exactly what survives weeks-to-months.
**Scope correction (2026-07-15, O106):** with `:core` pure JVM there is no "port the relay subset to non-JVM" for laptops/SBCs that run a JVM — you run the *whole engine* headless (no port, no subset, no second codepath).
The port idea survives only for genuinely JVM-less targets (bare LoRa gateways, tiny routers), if any survive the O104 hardware filter.

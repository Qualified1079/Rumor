# O240

**`[PART]`** Scheduled-message fire is not atomic and a failed fire looks like success (filed 2026-11-06; the fire-forever half closed as G69)

`scheduling/MessageScheduler.kt` `fireOne`:
compose then advance/delete are separate steps, so a crash between them re-fires on restart and concurrent `fireDue` calls can double-fire;
a compose that fails (no identity, DM contact not on file) still advances or deletes the row, with no failure state.
**Fix:** advance before compose with an idempotency key (message id derived from schedule id + fire time), and keep a failed one-shot DM for retry with a bounded attempt count.
No `:app` caller schedules anything yet, so this is latent.

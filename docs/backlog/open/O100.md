Original spec below.
Most people who hold a file hold the *whole* file — so if chunking is deterministic, many peers can seed the same content to one requester, spreading load and minimizing single-node bandwidth.
**What's missing today (verified):** `Chunker` keys chunks to a random per-send `transferId` (UUID), so the same file sent by two people produces two unrelated chunk sets, and `TransferAssembler` is single-source per transferId — **multi-source chunk recombination does not exist yet.** Required substrate:
(a) **deterministic content-addressed chunking** — chunk identity = `(hash-of-completed-file, index)`;
the completed-file hash is the "group name" every chunk carries, so a chunk from any seeder is interchangeable and a chunk always knows which group it belongs to;
(b) **multi-source assembler** — accept chunks for one group from many senders.
Three candidate fetch mechanisms (user-proposed), to be compared **in the simulator** before building for real:
**(A) active query** — broadcast "who has hash H?"; holders reply; requester selects which chunk to pull from which peer;
**(B) partial-transfer repair** — if someone hands you a file with chunks missing, request the specific missing chunk by `(group hash, index)` under that group name, from the original sender or anyone else;
**(C) passive piggyback** — regular traffic (messages, relaying, handshakes) appends "while I have you: got any chunks of H?";
if the peer has some but not the ones you want, keep looking.
(A fourth variant — provenance backtrace, asking who *they* got chunks from and querying up the chain — was considered and **rejected 2026-07-15**:
who-got-what-from-whom is exactly the social-graph metadata O27/O58 works to limit, and O29 breadcrumbs already capture the reverse-path signal passively.) Deliverable:
sim scenarios measuring delivery latency, per-node bandwidth, and load spread for A, B, C **and combinations** — the winner is chosen empirically, not by taste.
Cross-refs:

**Analysis (agreed 2026-07-15):** (i) **hard design constraint — per-chunk hashes (hash list or merkle root) inside the signed TransferMetadata.** Whole-file-hash-at-the-end can't attribute poisoning once there are multiple seeders;
per-chunk hashes make a bad seeder identifiable and evictable — without them one malicious node griefs every swarm it touches. (ii) Mechanism triage:
**B is nearly free** (CHUNK_REQUEST repair exists; it just needs group-hash identity) — build regardless of the sim outcome;
**C is the most Rumor-native** (extends the gossip summary to chunk inventory, rides existing machinery); **A is a flood-class spam surface** — rate-limit it.
(iii) **Sequencing:
content-addressed chunk identity is a wire-format decision — schedule immediately after the current reliability chain**, before more chunk traffic accretes on transferId identity.

# O213

**`[TODO/CODE]`** Room lifecycle ops arriving before their CREATE are dropped and never retried (found 2026-10-10 implementing O187)

**Found by a failing test, not by reading.** `handleRoomLifecycle` was first dispatched per-message via `scope.launch`, which raced CREATE against the INVITE that depends on it:
the invite ran first, found no room record to check moderator authority against, was dropped — and `ingest` had already recorded its id, so it was never re-offered.
**Partly fixed in O187:** lifecycle messages are now handled INLINE in `processIncoming`, so order *within one exchange batch* is respected, and an exchange commonly carries a room's whole history at once.
**Residual, genuinely open:** an INVITE or ACTION that arrives in an EARLIER exchange than its CREATE (different peers, different rounds — normal in a partitioned mesh) still finds no room, is dropped, and is dedup-marked so it never comes back.
Net effect:
a member can be permanently invisible to a node that happened to learn the room late, and a ban can fail to apply on exactly the nodes that most need it.
**This is O149's problem** (authority op-log conflict resolution + hash-linked causality) and should be solved there rather than patched here — the right shape is a small bounded hold-queue of lifecycle ops whose room is unknown, replayed when a CREATE for that roomId lands, with an eviction bound so it is not a memory sink (the O108 lesson).
**Do not "fix" it by re-offering dropped ids** — that reopens the dedup/censorship interaction the §2 ordering rule exists to prevent.
Interim mitigation that needs no new machinery:
a node that receives a lifecycle op for an unknown room could request the room's CREATE, but there is no room-metadata request type yet.
Cross-refs O149, O187, O152.
**Security-review finding (2026-10-10) absorbed here — replay/ordering of roster decisions.** `RoomInvite` carries only `expiresAtMs`, no issue time, and nothing records per-target last-applied state, so an UNEXPIRED invite issued before a KICK re-adds the kicked user on any node that applies it afterwards — and different nodes applying in different orders end up with divergent rosters.
The ban case is already closed (ban outranks invite, tested), the kick case is not.
**Concrete remedy, to land with O149 rather than alone:** add `issuedAtMs` to `RoomInvite` (bumping `rumor-room-invite-v1:` → v2, cheap while unreleased), keep a per-room/per-target last-applied timestamp or op sequence, and ignore any decision older than the current state;
persist applied decision ids so replays are idempotent.
Deliberately NOT improvised now — a partial ordering scheme over signed roster ops is precisely the state-resolution trap the O52/Matrix guardrail warns about, and a half-order gives false confidence.

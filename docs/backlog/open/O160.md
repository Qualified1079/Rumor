# O160

**`[DONE 2026-08-03]`** O32 routed/flooded TTL split is inert (filed 2026-07-30, audit #4)

**Fixed + redesigned (user-corrected).** First pass moved `decrementHops()` into the flood-fallback arm so routed hops preserve the flood budget.
User correction:
a flat "routed = 2× flood budget" ceiling missed the point — a routed hop is a directional unicast forward along a confirmed breadcrumb, so it should ride the trail *for free*, spending flood budget only where the trail runs out.
Final design: routed hops advance a count-up `routedHops` odometer bounded only by `MAX_ROUTED_HOPS=64` (a stale-trail/resource cap;
dedup is the real loop-breaker), preserving `hopsToLive`/`floodedHops` untouched; flood budget is spent only on the no-crumb fallback arm.
Removed the coupled `routedHops+floodedHops>MAX_TOTAL_HOPS` ceiling (the bug).
**Delivery-level validation (`SmartRoutingReachTest`) reframed the benefit honestly:
routing's win is TARGETING, not reach** — a routed DM touched 10/26 nodes (backbone path only) vs flood 26/26, same delivery to B;
reach itself is unbounded by `hopsToLive` for both (see O204). `PerPeerRoutingTest` de-fudged + a deep-routed-path test added. `:core`+`:simulator` green.

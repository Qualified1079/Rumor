# O207

**`[TODO/CODE+UI+DECISION]`** Presence sharing model + privacy toggle — drop unknowable "offline", scope last-seen sharing (filed 2026-08-06, user design question)

Two coupled changes to the O30/`OnlineStatusTracker` presence feature.
**(1) Honesty:** "OFFLINE" is unknowable — a silent peer may be dead, out of range, or duty-cycled asleep (O55).
Replace the ONLINE/RECENTLY/OFFLINE trichotomy with two *observed* facts:
**"last seen by you"** (first-hand `recordDirectContact`) and **"last reported online"** (second-hand `mergeRemoteStatus`, peer-asserted, skew-clamped per O128) — never assert a negative the node can't know.
**(2) Privacy scope (user's core ask):** presence is a genuine adjacency/social-graph leak (O51 — broadcasting last-seen lets a scanner reconstruct movement/contact graphs;
O58-Tier framing). Presence-sharing must be a UI toggle with scopes: **share last-seen with everyone / contacts-only / a whitelist / no-one (off)**.
Default should lean private (contacts-only or off) per the O27 honest-privacy posture.
**Open decision the user raised:** is showing presence at all worth the leak?
Value = knowing whether a peer is reachable/dead (feeds retry, custody-flush O202, routing liveness O198); cost = the adjacency leak. Likely answer:
keep it, but scoped + off-by-default for non-contacts, and note that the *routing* uses of presence (O198 liveness, O202 custody) rely on FIRST-HAND local observation which never leaves the device — only the *advertised* last-seen (O30 beacons / HELLO) is the shareable/leaky part this toggle gates.
Cross-ref O30, O51, O58, O128, O200 (notification privacy, under O143), O27.
**2026-10-11 (G58):** second-hand presence now travels as AGES on a monotonic clock (`_ext.ages`), not wall timestamps, and ONLINE is a 60s window with a 15s refresh — a redesign here should keep both.
Known cost to fold in: a duty-cycled MOBILE peer that links only every ~90s will flicker ONLINE↔RECENTLY;
"last seen by you, N ago" (this row's honesty proposal) sidesteps the flicker entirely.

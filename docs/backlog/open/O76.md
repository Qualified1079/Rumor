# O76

**`[PART]`** Per-payload compression + 6-bucket padding (text only), UI-transparent chunking above ceiling**

**Live end-to-end for DMs** (full pipeline detail archived in `docs/COMPLETED_GAPS.md`, O76 archive):
compose → deflate (raw RFC-1951) → pad to bucket → AES-GCM with `compressionAad(originalLength)` (= `"rumor-o76:<decimal>"`) as AAD → `_ext.c/cb/cl` → receiver decodes in `ThreadViewModel.decryptPayload`;
`compression-v1` is in `LOCAL_SUPPORTED_FEATURES`;
per-contact capability cache populated (`Contact.lastKnownSupportedFeatures`, schema v8) so future v2 features can gate per-recipient without architectural work.
Buckets 64/256/1024/4096/16384/65536 B; zero-fill padding (TLS 1.3 pattern — sensor-entropy "upgrades" rejected, rationale in `PaddingBuckets.kt`);
a relay tampering `cl` fails the AEAD tag; inflate has a zip-bomb cap. **Invariants:** TEXT contentType only, never BINARY/FILE;
**CRIME/BREACH** — never share a compression context across messages, never mix attacker-controlled bytes with secrets in one compression pass (audit any future group envelope before enabling compression there);
pipeline order is compress → pad → encrypt → sign → chunk; **UI seamlessness non-negotiable** — no UI ever exposes chunking or buckets.
**Not done:** (a) **>64 KB chunker fallback** — composeDirect currently falls back to uncompressed-and-unpadded above `PaddingBuckets.MAX_SINGLE_MESSAGE`;
proper fix is a `Chunker` split into a TEXT-typed thread + a new TextAssembler that stitches before display (multi-file work);
(b) **broadcast compression** — a separate decision (broadcasts have no AEAD layer to bind `cl` into; padding plaintext leaks `cl` to any observer;
compress-only-without-pad has bandwidth merit).

# G88

**O257 gossip catch-up: a session backfills flooded messages beyond the capped offer (2026-11-11)**

Found chasing a real-wire flood test that failed one run in five.
The offer is capped (50/100/200) before the peer's summary is known and keeps the freshest by sender clock.
On the bloom/id-list path, which is every store under the 3,000-message RBSR threshold, nothing outside that window was ever sent:
round two offered the same 200, the peer had them, and the session carried nothing. LanCatchUpTest over real sockets:
a fresh node meeting a peer holding 600 broadcasts received exactly 200 and stalled.
The same window is ordered by sender clock, so a sender with a slow clock, or a flood stamped in the future, kept a message out of it for good.

Fix:
GossipSession.backfillBeyondOffer spends the room left in the batch (up to 100, total 200) on stored messages the peer's summary lacks, chosen at random so a set the peer keeps rate-limiting cannot fill the room every round.
Flooded types only (BROADCAST and ROOM_*, FLOODED_OFFERABLE_TYPES):
the first cut also served DMs and LanLivenessValidationTest's baseline caught it handing a routed DM to a peer the engine's per-peer routing filter had excluded.

After: 600 of 600 in under a minute; all nine real-wire tests green. Cost: one (sentAtMs, id) store projection per bloom-path session.

Not changed: SimTransport takes-then-filters in the same way, so simulator scenarios with stores over 200 still model the old behaviour.

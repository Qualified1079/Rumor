# G37

**O98 Phase 3a coordinator (beacons→plan→hold) + self-echo/self-contact fix — field-verified on 3 phones (0.4.3-o98-selfpurge)**

The O98 substrate had no on-device driver:
nothing fired SELF_PRESENCE beacons and nothing ran the planner (`composeSelfPresence`/`PersistencePlanner` had zero `app/` call sites).
Added `core/routing/PersistenceCoordinator.kt` (pure brain:
recent-peer tracking → beacon adjacency → `assembleView` → `PersistencePlanner` → `PersistenceReconciler` hysteresis → `backbonePeers`) and drove it from `MeshService`:
a beacon loop (interval = `ModeEnvelope.presenceBeaconIntervalMs`, MOBILE floored to 90s so every node is visible to the planner — the beacon is a tiny CONTROL msg riding existing gossip, no extra radio wake), a 12s recompute loop that logs each change, an entry/exit pulse on mode change (O57/G12), and the plan gating the transport's `isPriorityPeer` so backbone peers get held links.
**Field result:** Samsung reached `view=3n/2e planned=2 held=2` (correct 2-link spanning backbone over 3 nodes), Moto/OnePlus held their piece and converged as beacons propagated — coordinator-free convergence confirmed on real hardware, zero crashes.
**Bug found + fixed (the beacon traffic surfaced it):** a node saw *itself* as an online contact. Two self-inclusion paths, both closed:
(1) **online-status echo** — a peer's exchange-time snapshot (`onlineStatusTracker.currentSnapshot()`, its whole map) includes *us*;
`GossipEngine.onExchange` merged it verbatim → self marked ONLINE → rendered as an unnamed bare-hex contact (also the "static shows up as a different userId" report — same root cause).
Fixed by subtracting our own userId before `mergeRemoteStatus`.
(2) **message echo → persisted self-contact** — a self-authored message relayed back hit `MessageStore.ingest` → `ensureContact(msg.senderId)` → **persisted a self row in Room** (survived `install -r`, which is why a reinstall didn't clear it).
Ephemeral SELF_PRESENCE isn't `ingestOwn`'d (unlike broadcasts), so it re-ingested every round. Fixed with one guard at the top of `processIncoming`:
a PEER-sourced message whose senderId is our own is always an echo → drop before ingest (covers every self-authored type).
Added a self-heal purge in `MeshService.startMesh` (`contactRepo.delete(identity.userId)`) so existing installs clear the stale row on next start — DB-verified on the Moto (0 self rows post-fix).
Also made `SimTransport` faithful: it hardcoded a single-entry `peerOnlineUsers` map, so the self-online bug was un-reproducible in sim;
now it shares the sender's real snapshot. Tests: `PersistenceCoordinatorTest` (5, core), `SelfEchoTest` (2, sim:
self-echo drop via MeshView + self-never-online). **Phase 3b (autonomous createGroup link realization) remains open on O98.**

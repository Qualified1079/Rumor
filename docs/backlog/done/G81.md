# G81

**O136 Explicit friending/accept mechanism — prerequisite for every trust tier (DONE 2026-07-22; archived 2026-11-08)**

Split out from O135(1) because it gates so much.
Today a contact is created automatically the instant a peer's message is ingested (`MessageStore.ensureContact`), and `isVerified`/`alwaysSave`/`displayName` are never set by a deliberate user gesture — so there is no machine-readable "I trust this person" signal for the O135 resource tiers, the O134 collapsible, the O21 verification, or the O135(4) vouch chain to key on.
Build an affirmative **friend/accept action** (button on the contact row + on first inbound DM + on nickname-set), persisting an explicit `friended`/`trustLevel` bit distinct from auto-persisted seen-peers.
Everything sybil-resistant downstream keys on THIS bit, not on "has exchanged." **SHIPPED:** `Contact.friended` + `ContactEntity.friended` (Room schema v10→v11), `ContactRepository.setFriended/isFriended` (interface + Room adapter + in-memory), `ContactDao` queries, a **Friend toggle** in the Contacts row overflow menu (`ContactsViewModel.setFriended`), and the O135(1) filter now keys on it:
`InboxPolicyManager.allowsInbox` drops non-friends when `friendedSendersOnly` (persisted toggle), own messages exempt, relay+store untouched. All suites green.
**Remaining:** the O135(1) Settings toggle UI for `friendedSendersOnly` (the bit persists;
needs a switch), a friend action on the thread screen + first-DM prompt (currently Contacts-menu only), and a live on-device validation.
Cross-refs O135 (tiers + vouching), O134 (seen-vs-known split, collapsible), O110/O113 (contacts UI), O111 (nickname), O21 (verify).

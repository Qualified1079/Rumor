# G38

**O98 Phase 3b field campaign (2026-07-17, 8 rounds on 3 phones, 0.4.6→0.5.4) — prompt-free credentialed backbone groups, field-verified**

The realization layer works on hardware:
autonomous `createGroup` honors the scanned-quiet channel every time (5745/5765/5785/5805/5825 all observed on-air via `dumpsys wifip2p`;
negotiated connect never honored any), credential joins land in 0.4–2s (vs ~60s negotiated) **with zero GO-side prompts — user-confirmed across a full cold-start convergence**, and a 3-node star ran stable for over an hour (hub GO + 2 clients, 10s sessions, 43–900ms).
**The design that survived contact:** (1) *credentials are self-contained in the SSID* — networkName = `DIRECT-`+12hex(SHA-256(`rumor-o98-net-v1:`+hostUserId)), passphrase = 16hex(SHA-256(`rumor-o98-psk-v2:`+networkName)) — so ANY node (bootstrap included, no beacons needed) joins a visible Rumor group prompt-free;
the `-psk-v1:` userId-derived variant is retired (never shipped beyond test phones).
(2) *Every durable Rumor GO runs the credentialed group* — a negotiated legacy GO converts ~15s after forming;
plain `connect()` into a formed group is the exact AOSP mechanism (`WifiP2pServiceImpl.notifyInvitationReceived`, WPS join-authorization) that raises the manual prompt, so Rumor never does it:
not at discovered GOs (`WifiP2pDevice.isGroupOwner` gate), not while a joinable backbone SSID is on air, not from Client-role nodes at all.
(3) *Radio ground truth gates plan actions* — clients act only when the target SSID is in Wi-Fi scan results (a P2P GO SSID is an ordinary scan hit);
junior would-be hosts defer while a lexicographically-senior backbone SSID is on air (clients all prefer the sorted-first SSID, so a junior group only splits the mesh);
90s "backbone memory" stops flap-window junk pairings; failed-join SSIDs cool down 3min (BUSY exempt — framework-busy, not group-absent;
note the framework also returns spurious ERROR on joins that then connect ~300ms later). (4) *Watchdog subtleties*:
groupCreated reaffirm must come from `requestGroupInfo` ground truth (the removeGroup→createGroup handoff delivers the old group's disconnect AFTER the new create's success callback — killed the group at +35s twice before the fix), the hold-guard must be evaluated at watchdog EXPIRY (async reaffirm race), and credentialed groups get 120s idle grace (clients' scan latency is 10–60s) vs legacy 35s — bounded, since a forever-held empty group deadlocks two view-blind converts.
**Bugs this campaign killed en route:** 48s create/kill cycle (stale-disconnect race), clients shredding working legacy groups chasing a group nobody hosted (round-2 destruction feedback loop — the hub's own view starves because it exchanges least, so legacy links must keep carrying beacons until the SSID is actually up), Samsung parked in a wrong group treated as healthy, conversion loops under a Client role, hub-flap churn pairing (user verdict:
unacceptable at scale — closed by dampeners (3)). Files:
`core/routing/{GroupCredentials,BackboneRealizer,ChannelSelector}.kt`, `PersistenceCoordinator.selfRole()`, `WifiDirectTransport` (backbone section), MeshService recompute hook.
Tests: `BackboneRealizerTest` (8), `GroupCredentialsTest` (6), `ChannelSelectorTest` (5). **Rounds 9–11 (0.5.4→0.5.6, user directive "fix the legacy thing"):
NEGOTIATED PAIRING RETIRED on API 29+.** Bootstrap-by-hosting:
a discovered peer with no backbone SSID on air → host your own credentialed group, never dial (the last 0.5.4 prompt came from a dialer whose stale *discovery* cache missed the target's GO flag — no gate on dialing survives cache staleness, so dialing itself had to go).
Both-host collisions resolve by seniority:
the junior (higher SSID) yields at its first 35s idle check AND joins the senior (a deferring host must join what it deferred to, or the planned hub sits isolated until view decay — field-caught).
Anti-churn set: Client-role nodes never initiate anything but their host's join; 90s backbone memory suppresses flap-window pairing;
junior would-be hosts defer to senior on-air SSIDs. **Final observation round:
`Connect initiated` count 0/0/0 across the fleet, zero prompts, full star converged through hosting + credential joins only.** The negotiated flow (tiebreaks, groupOwnerIntent, dual-role quirks) survives solely for pre-Android-10 devices.
**Known limitation:** SSID visibility is paced by OS foreground-scan throttling (4/2min) — a node can stay blind to a live group for minutes and bootstrap-host redundantly (self-heals via yield);
candidate fixes:
consume SCAN_RESULTS broadcasts instead of startScan nudges (event-driven, no quota — the throttle limits requesting scans, not reading results), or — the structural fix — **join by derived SSID without scanning at all**:
SSIDs derive from userIds, so any node that has heard a peer's beacon can compute the group name + passphrase and attempt the join directly;
the scan gate only prevents doomed joins and the cooldown machinery already bounds those.
**O104/O106 interop note:** because the passphrase derives from the SSID alone, a Linux node can join a phone backbone group as an ordinary Wi-Fi STA (wpa_supplicant + derived PSK, no P2P stack) — the desktop node gets phone-mesh interop nearly free.

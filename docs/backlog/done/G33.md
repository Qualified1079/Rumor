# G33

**O40 relay-deletion-on-ACK**

New `MessageType.MESSAGE_DELETE` (INFRASTRUCTURE class, MAX_BROADCAST_HOPS ceiling).
`MessageDeletePayload` carries `messageId` + `issuerPublicKey` + Ed25519 sig over `messageDeleteSignableBytes(messageId, issuerPublicKey)` (domain tag `rumor-message-delete-v1:`).
Issuer's userId is re-derived from the supplied pubkey and MUST match either the target DM's `senderId` or `recipientId` — third parties rejected.
`MessageRepository.deleteById` added across the interface + Room adapter + simulator stub.
`MessageStore.deleteById` is the engine-facing wrapper (id stays in the dedup set, blocking re-ingestion).
`GossipEngine.composeMessageDelete(messageId)` purges locally + broadcasts; `processIncoming` calls `handleMessageDelete` on any inbound MESSAGE_DELETE.
`MessageDeleteVerifier` (separate object, 7 commonTest cases — sender-deletes, recipient-deletes, third-party-rejected, tampered-messageId, bad-sig, target-missing-is-safe-noop, bad-base64-pubkey).
Tightens the FS exposure window for stored ciphertext: once recipient has read, all relays purge.
Does NOT recover FS against an attacker who already exfiltrated — bounds the FUTURE-compromise window only.
UI surface (a "delete from mesh" action) not wired yet; the protocol piece is complete.

# G48

**O108 transfer-metadata resource caps (2026-07-23)**

Three mechanisms, per the row's own triage: (1) **evidence-gating** — TRANSFER_METADATA now stores only a cheap record;
the NACK watchdog + retry loop arm on arrival of the FIRST real chunk (`handleChunk`), so a metadata with no chunk behind it costs one DB row and expires.
(2) **plausibility gate** — `Chunker.isPlausibleMetadata` (pure, tested) rejects inconsistent (`totalChunks != ceil(totalBytes/chunkSize)`) or out-of-cap (chunks>100k, chunkSize>1MB, bytes>1GB) claims before any state is committed — kills the `totalChunks=Int.MAX_VALUE` OOM.
(3) **per-sender concurrency cap** — `MAX_ACTIVE_PER_SENDER=8` in-flight receiving transfers;
excess metadata dropped not queued (Sybil beats per-identity caps — documented O27 floor; aggregate bound is O23 storage quota). Plus:
out-of-range chunk indices + oversized chunk payloads rejected at ingest;
abandoned transfers now release their chunk rows (`deleteAllForTransfer`), previously leaked. `ChunkerTest` extended (plausibility battery).

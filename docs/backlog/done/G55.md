# G55

**O205 mode-aware liveness routing window (2026-10-11)**

O198's liveness fallback keyed on a fixed 30 s "exchanged recently" window — ~3 rounds of a 10 s LAN cadence, but roughly ONE Wi-Fi-discovery beat for a duty-cycled MOBILE phone, so a quiet-but-alive link read as dead and the routed DM false-flooded, spending exactly the radio budget O55 conserves.
Now derived:
`ModeEnvelope.livenessWindowMs = LIVENESS_WINDOW_ROUNDS(3) * max(gossipRoundIntervalMs, wifiDiscoveryCadenceMs)` → MOBILE 90 s, STATIC 45 s, FREE 15 s.
The `max` is load-bearing (a node meets peers on its SLOWER beat);
FREE's `wifiDiscoveryCadenceMs = 0` means *continuous*, not instant, which is why it is a max and not a min or sum — pinned by a test.
`GossipEngine` takes an optional `modeState` (same nullable shape as MessageStore/Scheduler) and reads the window fresh on every use, so a mode transition needs no re-wiring;
`livenessWindowOverrideMs` (null default) beats the mode. No ModeState wired = the old constant, so nothing regresses by omission.
`ModeEnvelopeLivenessWindowTest` (:core) + `LivenessWindowModeAwarenessTest` (:simulator, real engines, SimClock, 45 s beat chosen to sit BETWEEN FREE's and MOBILE's windows so one topology separates the modes).
Teeth check:
holding the mode at MOBILE and pinning only the window back to 30 s re-breaks it, proving the outcome tracks the window value and not some other MOBILE-vs-FREE difference.

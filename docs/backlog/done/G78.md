Seed file owner-only from creation, written into the create handle (no reopen).
**Resolution:** `writeSeedOwnerOnly` creates the file with an atomic `CREATE_NEW` + `PosixFilePermissions.asFileAttribute(0600)` so on any POSIX FS it is never world/group-readable, not even briefly;
the write then truncates the pre-created 0600 file (perms unchanged).
Non-POSIX FS (no create-with-perms) falls back to a post-hoc `setPosixFilePermissions` and `RumorLog.w` on failure — a logged warning instead of a silently exposed key.
`NodeIdentityProviderTest` asserts the generated seed has no GROUP_READ/OTHERS_READ (POSIX-gated via `assumeTrue`). Original finding below.
— `node/.../NodeIdentity.kt:57-61` creates the private-key seed file at default perms, THEN chmods to 0600 — a real (brief) window where a fresh identity file is world/group-readable on a shared machine.
Worse, the `Files.setPosixFilePermissions` call is wrapped in `runCatching` with no failure logging — a non-POSIX FS or unrelated I/O error leaves the file at default perms silently.
`TEST INSTRUMENT ONLY` today per its KDoc, but O44 designates this file's descendant as the product `:node` identity impl — get the create-with-restrictive-permissions-from-the-start pattern right before that promotion, not after.
Cross-ref O44, O106.

# G68

**O231 (half) transfer hash-mismatch wedge → FAILED; cancel guarded; reassembly serialised (2026-11-06)**

When `Chunker.reassemble` returned null (signed content hash mismatch) `attemptReassembly` returned without cleanup and the watchdog's all-chunks branch called it and exited past its own cleanup:
the transfer sat IN_PROGRESS forever holding a `MAX_ACTIVE_PER_SENDER` slot, and no NACK could repair it (no index missing). `FAILED` was never set anywhere.
Now a mismatch first discards the chunk rows and re-arms the watchdog to re-fetch them, up to `MAX_REASSEMBLY_REFETCHES` (2) times, then sets FAILED and releases the per-sender slot, chunk hashes, pause flag, chunk rows and watchdog.
(The first cut went straight to FAILED;
a background security review pointed out that chunks come from any seeder and that after a restart the signed per-chunk hashes are gone, so one poisoned chunk would have killed a genuine transfer outright.
Honest senders always include per-chunk hashes, so outside that window poisoned chunks are already dropped at ingest.) `cancel()` now applies only to an IN_PROGRESS RECEIVING record (it used to overwrite COMPLETE, and on a SENDING record sent TRANSFER_CANCEL to our own id).
Reassembly is serialised per transfer (`reassembling` set) so ingest and the watchdog can't both complete it, and the watchdog is cancelled LAST in both outcomes — cancelling it first, when the watchdog itself is the caller, made the following suspending repo writes throw on a dispatching (Room) repo.
Tests: `TransferAssemblerTest` +3 (one mismatch discards the chunks and the honest re-send then completes;
a mismatch persisting past the re-fetch budget ends FAILED and frees its per-sender slot, with an at-cap control; cancel leaves COMPLETE alone);
teeth-verified for the re-fetch, the FAILED path and the cancel guard.
**Not done:** a FAILED transfer cannot be re-registered by re-announcing its signed metadata (`handleMetadata` returns on any existing record).
**Untested:** the reassembly guard and the cancel-last reorder — in-memory repos never suspend, so neither race is reachable in a JVM test;
both are reviewed only. O231 stays open for pause/restart/CAS. ELI5 §4.

# G84

**O213 room ops that arrive before their CREATE are held and replayed; a batch applies room history in signing order (2026-11-11)**

Reproduced live on a three-node :node line:
a restarted node received a room's invite, ban and unban before its ROOM_CREATE, because the store backfill offers freshest-first;
all four were dropped as from a non-moderator and dedup-marked, so the node kept an empty roster and no bans.
The 2026-10-10 inline-handling fix assumed a batch arrives oldest-first, which it does not.

Fix, both in RoomMessaging:
(1) GossipEngine.onExchange processes a batch through historyFirst, which puts room lifecycle messages first with the CREATE leading and the rest in sentAtMs order (signed, so a relay cannot reorder);
(2) an INVITE or ACTION for a room with no record is held in a bounded queue (32 rooms x 64 ops, oldest room evicted) and replayed through the full signature and moderator checks when the CREATE is applied.

Tests: RoomHistoryOrderTest (baseline in-order, newest-first in one batch, ops an exchange ahead of the CREATE, and a forged moderator op held then refused).
The three out-of-order tests were red before the fix. Verified live: a restarted node rebuilt members and bans identical to its peers.

Still open under O149:
two ops for a room that is already known, arriving in different exchanges in the wrong order (unban before ban) are applied in arrival order.
SentAtMsLintTest allowlists RoomMessaging for the ordering key.

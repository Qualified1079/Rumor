# G50

**O39 per-message key-lifecycle re-audit — merged compress + sealed-sender paths (2026-07-23)**

Traced the full per-message key path through `composeDirect` (O76 compress + O53 sealed-sender), `ThreadViewModel.decryptPayload`, `SealedSenderKey.derive`, and `MultiRecipientEnvelopeCodec`.
**Findings: (1) constant HKDF salt is CORRECT — not a bug.** Per-message key variation comes from the fresh ephemeral X25519 key → unique ECDH `shared`;
the `"RumorDH"` salt is a domain tag, and a constant salt in HKDF-extract is exactly per RFC 5869.
The O39 "buried per-message-salt assumption" was the thing to check; it holds because the ephemeral key, not the salt, provides freshness.
**(2) REAL residual gap fixed:
`CryptoManager.x25519Agreement` never zeroed the raw ECDH secret.** Every call site diligently zeroed the *derived* key, but the raw `shared` survived to GC inside the function — and since the salt is public+constant, a leaked `shared` re-derives the AES key, making the call-site zeroing worthless.
Fixed with `finally { shared.fill(0) }`, centrally benefiting all consumers (DM compose/decrypt, sealed-sender, room envelopes).
Byte-transparent (return value unchanged; all golden vectors + roundtrip tests pass). Pinned by `SourceInvariantTest` invariant 7.
**(3) sig-scope confirmed clean:** `signableBytes` covers `encryptedPayload` (ciphertext), never plaintext — no Bridgefy-style UKS/surrogate-signature surface;
O76 `_ext.cl` tamper-evidence rides the AEAD AAD (not the sig), as designed. Sealed-sender/room codecs already zeroed contentKey/wrapKey/ephemeral.

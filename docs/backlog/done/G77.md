# G77

**O172 `Rbsr.respond()` has no per-round frame-count cap — CPU-exhaustion DoS (filed 2026-07-30, audit #15) (DONE 2026-07-31; archived 2026-11-08)**

**RESOLVED.** Added `MAX_RBSR_FRAMES_PER_ROUND = 10_000`;
`respond()` processes at most that many frames per call (`incoming.subList(0, cap)`), bounding the O(frames × N) store-scan work a ~30k-frame flood could force.
Far above any honest delta-sync round; with `MAX_RBSR_ROUNDS=12` it caps total per-session work.
Over-cap frames reconcile on later rounds (graceful partial progress, same policy as `MAX_RBSR_SESSION_IDS`).
`RbsrFrameCapTest` proves the cap via a call-counting storage (flood → exactly cap scans; under-cap batch → all processed). NOTE:
the row also mentioned a cancellation checkpoint — `respond()` is a pure non-suspend function, so that belongs to the `GossipSession` calling loop (unchanged here).
Original finding:
`core/sync/Rbsr.kt:198` — a single ~4MB packet can carry ~25-30k Fingerprint frames, each an O(N) linear scan over the full local item set with no cancellation checkpoint.
DoS surface aimed exactly at large-store anchor/backbone nodes (the ones O55/O98 most want to keep alive). Fix:
cap frames processed per round + add a cancellation checkpoint. Cross-ref O42/G24, O98.

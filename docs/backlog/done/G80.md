# G80

**O132 Broadcast size cap — large text broadcasts are monolithic, never chunked (filed 2026-07-22, live-test finding) (DONE 2026-07-22, commit a2a98bd; archived 2026-11-08)**

**RESOLVED — all three parts shipped + simulator-tested (`OversizedMessageTest`):** (1) **compose cap** — `composeBroadcast` (GossipEngine:389) and `composeRoomMessage` (:724) refuse text over `MAX_BROADCAST_CONTENT_BYTES` (64 KB, the largest padding bucket);
(2) **ingest drop** — `MessageStore.ingest` (:210) records the id as seen (so a re-offer fast-drops) then returns false for any BROADCAST/ROOM_MESSAGE over 64 KB → never stored, never relayed, never in an offer batch;
(3) **send-side offer skip** — the offer builder (GossipEngine:904-918) skips any message whose `approxWireBytes()` exceeds `MAX_OFFERABLE_MESSAGE_BYTES` (1 MB) and trims the batch to `MAX_OFFER_BATCH_BYTES` (3 MB), so a legacy/oversized message is skipped rather than sent-and-reset — the head-of-line poison loop is broken on every honest node.
The raw `GossipSession` frame guard (`require(len in 1..4_000_000)`) still throws for a genuinely malicious >4 MB frame, but since honest nodes never store/offer such a message there is no re-offer loop;
a malicious sender only resets its own single session.
**Original finding retained below.** **Text broadcasts have NO size cap and are NEVER chunked** (chunking = `Chunker`/`TransferSender`, file-transfer-only).
`composeBroadcast` builds whatever size it's given; `trafficClass` only downgrades oversized payloads to BULK *priority*, it doesn't split or reject.
So a 500 KB / 1 MB / 10 MB text broadcast becomes ONE giant signed message relayed whole to every peer and stored whole — a bandwidth/storage amplifier on every relay (O108-family, remotely triggerable, no auth).
The global room is text-only by design (O36), so there is no legit multi-MB-text use case.
**Fix (NOT chunking — broadcasts are gossip, not point-to-point transfers):
a hard size cap on broadcast text at BOTH compose (refuse to send / warn) and ingest (drop oversized `BROADCAST`/`ROOM_MESSAGE` before store+relay).** Pick the ceiling deliberately — 16 KB (INFRASTRUCTURE ceiling) is plausibly too tight for a legit long post;
64 KB (largest padding bucket) is a reasonable cap. Enforce structurally like the other `trafficClass` ceilings so a cracked client can't bypass.
The 0.6.10 `capForDisplay` (O112) stops the *display* crash but the oversized message still rides the wire and fills storage — this row is the structural half.
**Live-measured boundary + a HEAD-OF-LINE-BLOCK bug (2026-07-22, `:node` vs OnePlus):** the `GossipSession` frame guard is `require(len in 1..4_000_000)` (`GossipSession.kt:398`) — a legit anti-OOM defense against a malicious length prefix.
Messages **under 4 MB propagate + store fine** (1 MB verified end-to-end, monolithic but works). A message **over 4 MB is worse than wasteful:
the guard `throw`s → connection reset → the whole session dies, AND the oversized message stays in the sender's store/offer batch, so it is re-offered every round → every subsequent session resets on it → nothing else syncs to that peer (head-of-line block, verified:
a tiny broadcast sent after a 5 MB one never reached the phone).** One oversized broadcast permanently wedges a link.
**Mesh-wide confirmation (3-phone + node run):** injecting ONE 5 MB broadcast at the node put ALL 3 peers into repeating `Session error`, and a tiny broadcast sent right after reached **none** of them — i.e.
a single oversized message a node holds wedges its sync to **every** peer at once (denial-of-relay;
that node becomes a black hole until the message is evicted).
Self-limiting for a *malicious* sender (it mostly hurts their own outbound), but catastrophic for any *honest* node that ingests a >4 MB message (legacy build, bug, or pre-cap peer).
**So O132 needs THREE parts:** (1) compose-time cap (refuse to send oversized); (2) ingest cap (drop oversized before store+relay); (3) **send-side:
never offer a message whose frame would exceed the peer's limit — skip it, don't attempt-and-reset** (and/or receiver skips-and-continues instead of killing the session), so a message that slips past (legacy, large DM) can't poison the link.

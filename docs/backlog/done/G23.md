# G23

**O92 reseed-from-store on mesh start**

The outbound `Scheduler` and `DuplicateFilter` are volatile;
`messagesForExchange` drained the scheduler, so a restarted phone offered nothing though its repo was full ("0 sent, 0 received").
`GossipEngine.reseedFromStore()` (called from `MeshService.startMesh`) now does two reseeds:
**scheduler** ← `MessageRepository.offerable(limit)` (`BROADCAST`/`DIRECT` with `hopsToLive>0`, freshest-first — control/transfer/presence traffic is time-sensitive and deliberately excluded), and **DuplicateFilter** ← `MessageRepository.knownIds(limit)` (all recent ids, via new `DuplicateFilter.seed()`) so the peer-summary check reports what we actually hold and peers don't re-offer it.
`wasRelayed` does not gate reseed (it means "manually hop-boosted", not "delivered");
reseed carries stored `hopsToLive` with no hop mutation, so the peer's want-set still dedups → no re-flood.
Repo methods added to all impls (Room DAO uses the `ttl` column; InMemory). Test:
`simulator/…/engine/SchedulerReseedTest.kt` (models restart as a fresh engine over a shared repo;
asserts empty offer pre-reseed, correct offer/exclusions + accurate summary post-reseed).
**Residual (deeper follow-up, not the filed symptom):** `scheduler.take()` is still destructive *within* a session, and reseed runs only on start — sourcing `messagesForExchange` from the durable repo directly (instead of a drain) is the real fix for continuous multi-peer re-offer, and pairs with O40 (relay-deletion-on-ACK) to prune delivered DMs since there is still no per-message delivered/ACK state to filter on.

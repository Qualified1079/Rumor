# G54

**O212 payload metadata signed — `rumor-msg-v3:` (2026-10-10, bundled with G53)**

v2 framed only `payload.content`, so `contentType`, `filename`, `mimeType` and `sizeBytes` were **relay-mutable**:
the sender authenticated the bytes but not what they claimed to be.
Found empirically — an O186 test asserting "retyping TEXT→IMAGE must break the signature" FAILED, which is also a caution about reasoning from the invariant list instead of from `signableBytes`.
Impact was not cosmetic:
it manufactured a censorship primitive out of any contentType-dependent drop (retype a TEXT feed post → honest node drops it → if the drop had burned the id, the genuine post is refused as a duplicate everywhere downstream), and `filename`/`mimeType` drive O14's extraction warning, so a relay could change what a receiver is told it is about to open.
**Fixed** by framing all four fields unconditionally under the new `rumor-msg-v3:` tag (hard cutover, pre-release, same justification as O144's v2).
O186's workaround (drop before the record-as-seen commit) is deliberately KEPT:
signing contentType removes the cheap retype, but an honest-but-wrong client's non-TEXT post still should not burn a shared id, and the ordering costs only a re-offer.
**Process notes worth keeping:** (1) `DomainTagInvariantTest` passed throughout the bump because `assertContainsTag` greps the FILE and a stale KDoc still said v2 — a behavioural companion test now asserts the bytes the signer actually emits, since a comment is not evidence;
(2) `SignableFramingGuardTest` also never caught this, because the bug was an OMITTED field rather than a bad delimiter — teaching it to catch omissions is still open.

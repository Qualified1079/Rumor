— Original spec: Today every message goes on the wire as raw plaintext (broadcasts) or raw ciphertext (DMs), uncompressed.
For text-heavy traffic (chat, status updates, broadcast feed) typical content compresses to 30–50%.
Worth taking — but only for `MessagePayload` of TEXT contentType, never for BINARY/FILE which is already compressed (re-running gzip on JPEG burns CPU for no gain).
Pipeline order is **compress → pad → encrypt → sign → chunk**: zstd or deflate the plaintext;
pad with zeros up to the smallest bucket that fits in `{64 B, 256 B, 1 KB, 4 KB, 16 KB, 64 KB}`; AEAD over the padded blob; outer Ed25519 as today.
Six buckets ≈ 2.6 bits length leak per message vs full byte-length of raw plaintext today. Worst-case overhead capped at ~4× (content just over half a bucket).
Buckets chosen for the real content distribution: quick replies / acks fit in 64 B without 50× overhead; typical chat in 256 B; paragraphs in 1 KB;
blog-length posts in 16 KB without auto-chunking; only true outliers above 64 KB chunk.
Top bucket exceeds the 16 KB INFRA/REALTIME ceiling so anything above 16 KB demotes to BULK class anyway.
**UI seamlessness — non-negotiable.** User composes a message of any length in one input box; compression + bucket selection are invisible.
Compressed payloads up to 64 KB ride a single wire message.
Above 64 KB the existing `Chunker` (file-transfer path) splits into a TEXT-typed thread with sequence metadata;
recipient's TextAssembler stitches them back into a single logical message before display.
The user types, the recipient reads — no UI ever exposes "your message was chunked" or "this is the 3rd of 5 fragments." Wire-format addition routes through O37's `_ext`:
a new boolean `compressed: true` on the wrapper plus a bucket-id byte;
absence means uncompressed (back-compat with peers that don't advertise the capability via HELLO `supportedFeatures: ["compression-v1"]`).
**CRIME/BREACH constraint:** never share a compression context across messages, and never mix attacker-controlled bytes with secret bytes inside the same compression pass — current DM model is safe (sender controls 100% of plaintext) but any future group-chat envelope (O52) or any header that mixes a session token with user content must audit before turning compression on for that path.
Padding bytes are zeros (TLS 1.3 pattern);
the AEAD makes ciphertext-pad indistinguishable from anything else regardless of pre-encryption content — mixing in OS sensor entropy (gyro, temp, camera) is a footgun, not an upgrade:
a CSPRNG cannot be made stronger by XORing low-entropy sources, and reading sensors adds permission prompts, battery drain, and a fingerprinting vector.
`SecureRandom` (kernel-seeded from boot-time hardware entropy + interrupt jitter) is what every well-reviewed protocol uses; trust it. Honest framing:
bandwidth win on text, no win on media (covered separately by O19 pre-send compression UX), modest fingerprinting reduction (6 buckets instead of every length distinguishable).

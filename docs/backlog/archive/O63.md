# O63 (archive: shipped-substrate record of a row that is still open or decided elsewhere)

**`[DECISION]`** iOS via shared `:core` (KMP), not a separate app**

If iOS ever ships, do it by promoting `:core` to Kotlin Multiplatform with `commonMain` + `jvmMain` + `androidMain` + `iosMain` (and `linuxMain` for headless relay nodes per O54).
A separate-but-interoperable iOS app is rejected:
two protocol implementations diverge silently, and the wire is the only place a bug is unrecoverable post-ship. Hard constraints, in order — do not skip ahead:
(1) **Define stable storage interfaces in `:core` before any SQLDelight migration.** Today `MessageRepository` / `ContactRepository` / `RouteRepository` / `BreadcrumbRepository` / `BlocklistRepository` / `TransferRepository` / `ChunkRepository` / `ScheduledMessageRepository` exist as core interfaces — keep it that way.
DAOs (Room today, SQLDelight tomorrow, Core Data never) must not leak past the adapter layer. Anything in `:core` that imports a DAO type is the bug.
(2) **`:core` compiles unchanged on JVM, Android, Linux, iOS.** Protocol, routing, scheduler, crypto, chunker, blocklist, RBSR, breadcrumb cache, dedup, wire-format — all `commonMain`.
Platform deltas (Keystore vs Keychain, Room vs SQLDelight vs in-memory, BLE stack, time source, secure random) hide behind `expect/actual`.
The simulator already proves the storage interfaces are honest — if it compiles against in-memory repos, it'll compile against SQLDelight repos.
(3) **Plugin loading needs a more dynamic path before ecosystem ships** (per O15+O24+O26). DEX-only is Android-only by construction;
iOS forbids runtime code load entirely. For cross-platform ecosystem the plugin contract has to be expressible without arbitrary code execution on the host:
declarative manifests + a constrained capability surface (message filters, display transforms, envelope codecs declared as data, scheduled-message templates).
Native-code plugins stay Android-APK-tier; the declarative tier runs on iOS and locked-down Android profiles. iOS-specific work when the time comes:
SQLDelight Native driver, CryptoKit-backed `actual` for Ed25519/X25519/AES-GCM (or stick with BouncyCastle-Kotlin in commonMain — slower but one impl), Core Bluetooth wrapper for BLE peripheral+central, MultipeerConnectivity as Wi-Fi-Direct analog (no true equivalent — iOS won't hold a Wi-Fi-Direct group open).
None of that is worth doing until (1) and (2) are done;
(1) and (2) are worth doing regardless of iOS because they also unlock O54 (Linux relay nodes on routers/SBCs).
(4) **No Android feature regression when iOS lands.** Adding iOS must never remove or weaken anything that works between two Android peers.
iOS may ship a strict subset (no Wi-Fi Direct, part-time relay, no DEX plugin loader on App Store) — that is acceptable. What is NOT acceptable:
cutting capabilities from Android because iOS cannot host them. Inter-Android exchanges may carry more than Android↔iOS or inter-iOS exchanges;
the protocol stays interoperable across all three pairings by negotiating per-session through HELLO `supportedFeatures` (the same machinery G10 already uses for RBSR).
Reviewer test for every change touching a cross-platform feature: "does this still work for two Android peers talking to each other?" If no, reject.
iOS limitations are negotiated *down* per session, never enforced *upward* onto Android.
**Post-merge note (2026-07-16):** the KMP layout itself was flattened to plain JVM in the merge;
the `core/platform/` shim layer and `ios/` bridge spec were kept precisely so this decision stays cheap to execute later — re-splitting is per-file mechanical.

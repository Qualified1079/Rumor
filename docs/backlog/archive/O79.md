**`[PART]`** Rooms — unified open / invite / password / closed-membership shape (subsumes O52 group chats;
allowed by default per O36)** — **wire vocabulary substrate landed; threat model + design decisions recorded;
multi-recipient envelope architecture chosen.** **Encryption architecture decision (recorded):** two room modes only — **OPEN** (plaintext signed broadcasts, addressed to a routing tag;
no encryption since the room is publicly readable by definition) and **ENCRYPTED** (multi-recipient envelope:
one AES-encrypted message body + N small per-recipient key wraps, where N = current member count from the events-derived membership).
**No shared room key, no ratchet.** Member kick = omit from the next envelope's recipient list.
Per-message forward secrecy is automatic (each envelope uses fresh ephemerals). Wire bandwidth per message ≈ `content + 48 × N` bytes. At 50 members:
~2.6 KB per 256-byte message; at 1000 members: ~48 KB.
Sender CPU is O(N) key wraps per send — noticeable but tolerable at room sizes Rumor's mesh deployment actually targets.
PASSWORD mode is folded into ENCRYPTED via password-derived membership token rather than a distinct shared-key path.
**What this collapses:** O89 ratchet design problem evaporates (no shared key to rotate); member-key rotation cascade evaporates;
"catch-up after missing rotation" flow evaporates. O89 reduces to just write-enforcement via posting certificates.
**Routing decision (recorded):** per-message HMAC tag `T_msg = HMAC(roomKey-or-roomId-derived-key, messageId)` carried on the wire instead of plaintext `roomId`.
Observers cannot enumerate roomIds or cluster messages by Room. Cost: relays can't preferentially forward to known-room-subscribers.
Acceptable given O76 compression bandwidth headroom.
**Membership decision (recorded):** events-derived (RoomCreate + cumulative invites/joins/leaves/bans replayed) with an in-memory projection cache for O(1) lookups.
Source of truth is the signed event stream; cache is the projection. **Channels-within-rooms decision (recorded):** `payload.channel:
String?` metadata field on room messages. UI filters by channel; protocol carries the field unchanged.
Channel WRITE permissions are deferred to O89 (much smaller now).
**Threat model recorded:** `docs/ROOMS_THREAT_MODEL.md` walks each defense layer and the structural-enforcement rule (no honor-system policies — every security-affecting policy is cryptographic or it isn't enforced).

The substrate is enough to fuzz the wire surface and pin the SerialName strings in the never-reuse policy. Original spec (preserved):
One protocol primitive serves the full spectrum from open public chats to closed-membership groups — the difference is membership policy and per-message crypto.
**Wire shape (one schema, four membership modes):** room creation signed by creator (`roomId = SHA-256(name || createdBy || createdAtMs)`);
membership policy `{ open | invite | password | closed }`; posting policy `{ member_only | mod_approved | anyone_with_mod_removal }`. **Open**:
anyone can join by roomId; messages are plaintext. **Invite**:
joining requires a signed `RoomInvite { roomId, invitedUserId, roomKey, expiresAtMs, modSig }` DM from a moderator carrying the room's symmetric key.
**Password**: room key derived from `Argon2id(password, roomId-as-salt)`; anyone who knows the password can derive K;
supports printed-on-flyer / shared-by-voice deployment. **Closed**: explicit member list, K distributed per-member via signed key DMs (per O52 crypto).
All modes addressed-to-roomId; **non-subscribers receive nothing for that roomId** (relay drops; not just UI filter).
**Media attachments policy is the Room creator's call** — when someone creates a Room they decide whether to allow image/voice/video/file attachments.
The only hard exception is the **global Room** (the singular shared roomId, if exposed):
it has no creator and cannot be moderated at scale, so media is off there at the protocol layer (see O36).
Every other Room inherits whatever its creator picked at Room-creation time. **Moderators:** room creator is mod-by-default;
can grant additional mod keys signed by themselves; mods can grant other mods (transitive but each grant signed and revocable). Alternative path:
member-elected mods via signed votes, top-N become mods, configurable quorum / rotation cadence.
**Moderation actions:** signed `RoomAction { roomId, target, action: REMOVE_MESSAGE | KICK_USER | BAN_USER, reason, modSig }`.
Peers honour the action if `modSig` verifies against the current mod set. Anti-abuse integration: Room can subscribe to O67 filters as policy;
Room can publish its own block list (sibling of personal blocklist, signed by Room mods) so banned users' content is dropped at every member's client.
**@-mention notifications** become a first-class wire surface:
new `MessageType.MENTION` with `mentionedUserId`, INFRASTRUCTURE-tier, surfaces in the mentioned user's notification feed (covers "@ a mod" UX for moderated Rooms, plus general DM @-mentions, plus O68's report-to-mod delivery).
**UX-only differences between "Room as group chat" and "Room as public space":** member-list visibility (group chat shows roster; open Room may not);
join/leave events (group chat surfaces them; open Room may not); thread vs feed presentation. These are display-layer choices, not protocol-layer distinctions.
Per-Room creator-mod or elected-mod with explicit remove/kick/ban actions is the content-moderation primitive that scales without a central authority — each Room's creator (or elected mods) is the human-in-the-loop for that Room.
Every user can leave or join any Room at will; the global Room is text-only because it cannot have a creator-mod.
**Open design questions:** moderator key rotation when a mod leaves / is compromised (NOT borrowing O41/G9 shape since that's deprecated — design a manual-confirm-by-Room-members flow);
conflict resolution when two mods take contradictory actions (lean: last-action-wins with public audit log);
Room forks when policy is contested (any user can fork; same membership-list seed, new roomId);
author edit / delete within Rooms (covered by O40 relay-deletion + new "allow author delete" Room-policy bit). **Status:** Significant design work;
one of the larger backlog rows.
**Membership guardrail (session-B, binding for the remaining work):** group membership is an authored, signed, per-room append-only op-log with a trivial merge — strictly separate from message ordering, NEVER state-resolved from the message DAG.
This is what inoculates Rooms against Matrix's state-resolution failure class. Subsumes O52.

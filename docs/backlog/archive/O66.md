# O66 (archive: resolved or moot row)

**`[DECISION]`** RBSR perf characterization (informs O42 promote-to-default gate)**

Not a blanket "negligible." Three regimes:
**(a) Steady-state, small symmetric diff (≤dozens):** RBSR is *cheaper* than bloom — handful of 32-byte XOR fingerprints, no false-positive risk, no `expectedItems` to guess.
Decisive bandwidth win once the diff exceeds ~50 items.
**(b) Cold-start (one peer has zero):** degenerates into "send the id list" — same as bloom+offer-batching today. No win, no loss.
**(c) Partition-heal (both sides thousands of items, large diff):** the interesting case. Each round bisects keyspace by 16;
G17's bump to `MAX_RBSR_ROUNDS=12` makes the cap a recursion safety (16¹² leaf ranges), not a budget.
CPU per round is O(items-in-range) for the XOR fingerprint — noise.
Real cost is **latency** (each round = one round-trip), which is exactly what scenario 14 was hitting.
G17 added `ExchangeMetrics.rbsrRoundsUsed` so the promote-to-default gate is "convergence ≤4 rounds on realistic heal traces" measured from data, not vibes.
Until that gate passes, `LOCAL_SUPPORTED_FEATURES = emptyList()` stays — opt-in per session via simulator toggle.

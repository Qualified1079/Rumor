# O99 (archive: full tombstone record)

**`[SUPERSEDED → folded into O98]`** Channel-aware group creation (don't disrupt nearby Wi-Fi)**

**Merged into O98.** Rationale (concluded 2026-07-13 after an on-device spike):
O99 split into two halves — *host election* (who creates the group), which is entirely O98's job, and *channel selection* (createGroup on a scanned-quiet 5 GHz channel), a ~40-line primitive with no standalone existence (it needs an elected host to call it, and robust host election under partial discovery + the member cap **is** O98).
The spike also proved standalone O99 can't work:
negotiated `connect()` ignores the channel hint (only autonomous `createGroup` honors it), `createGroup` joins need a manual WPS accept, and naive multi-host election fragments.
All actionable detail + field findings now live in the O98 row under "Channel selection (absorbed from O99)".
Kept as a tombstone so the connect()-hint-is-ignored finding isn't rediscovered the hard way. Original concern preserved below for context. Field concern:
forming a P2P group near an *unrelated, unconnected* Wi-Fi network can degrade/drop it — feels like an accidental jammer.
This matters enormously for present-day casual use (in SHTF/infra-down, O55, there's nothing to disrupt).
**Physics reframe:** Wi-Fi is CSMA/CA (listen-before-talk); a compliant P2P GO *cannot* RF-jam — the radio waits for a clear slot and shares airtime.
What was observed (bystander 5 GHz dropped) is added contention on a shared channel **plus** STA channel-switch churn pushing a *marginal* link over the edge — a channel-selection problem, not a fundamental one.
**Root cause in code:** `WifiDirectTransport.kt:307` builds `WifiP2pConfig` with only `deviceAddress` + `groupOwnerIntent` — no band/channel hint, so the OS picks arbitrarily (defaulted to 5 GHz ch 36 in the field).
**Fix (all Android-API-supported, GO-side only):** (1) **Scan-then-pick the empty lane** — before `connect()/createGroup()`, read `WifiManager.getScanResults()` (location already held) to see occupied channels, pick the least-occupied one.
Auto-channel-select, same as a well-behaved router.
(2) **Prefer 5 GHz** via `WifiP2pConfig.Builder.setGroupOperatingBand(GROUP_OWNER_BAND_5GHZ)` — far more non-overlapping channels than 2.4 GHz's three, shorter range = smaller interference footprint, and it keeps 2.4 GHz clear for BLE discovery (BLE is 2.4).
(3) **Request the chosen channel** via `setGroupOperatingFrequency(mhz)` (driver may override — device-dependent, hence the HW tag).
(4) **If no empty channel exists, land CO-channel with the strongest neighbor, never adjacent** — co-channel shares via CSMA/CA (degraded but polite);
adjacent/overlapping channels cause un-arbitrated energy overlap that corrupts frames and is *worse*.
(5) **Minimize dwell time, mode-dependent (O57):** Mobile mode → form on-demand for the transfer then tear down (small footprint);
Free/Static (plugged-in anchor) → hold the persistent link (accepts footprint for instant delivery). This trades against O2/G19 persistent links deliberately.
Only the GO selects the channel, so GO-election must run the scan.
**Honest ceiling:** in fully-saturated RF you still add contention (no worse than any hotspot/Chromecast, never jamming);
channel-awareness turns "random disruptor" into "quiet, polite neighbor." Does not change the BLE-rendezvous→Wi-Fi-Direct-bulk model — only which lane it picks and (in Mobile mode) whether it squats there.
**Field finding (2026-07-13) — the connect()-hint approach does NOT work:** implemented `setGroupOperatingFrequency` on the negotiated `connect()` config (scan-picked quiet channel) and verified on all three test phones — the driver **ignores it**.
Moto requested ch149, OnePlus ch153; both groups formed on ch36/40 (`freq=5180/5200` in wpa_supplicant `P2P-GROUP-STARTED`).
Negotiated connect always uses the driver's default 5 GHz operating channel. Samsung (API 31) additionally *rejected* the Builder outright:
`IllegalStateException "network name must be non-empty"` when a frequency is set without a network name.
Change was reverted (kept the tree honest — provably ineffective on our only hardware).
**The only mechanism that controls the P2P channel is autonomous `WifiP2pManager.createGroup(channel, config, listener)`** with a full `WifiP2pConfig.Builder().setNetworkName("DIRECT-…").setPassphrase(…).setGroupOperatingFrequency(freq).build()` — the device unilaterally brings up the group on the chosen channel and clients follow.
That is a real rearchitecture of GO election (today it's negotiated via `groupOwnerIntent`;
autonomous-GO needs one side to *decide* to create and the others to join by network name/credentials), touching the hard-won G18/G22/G19 connection flow — scope it as such, with careful on-device regression testing.
The `preferredGoFrequencyMhz()` scanner (scan → least-congested non-DFS 5 GHz channel) is the reusable piece; only the group-formation call changes.

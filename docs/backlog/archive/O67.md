the reserved kind-id is `rumor-project-default-lists-v1`. Pieces shipped:

separate data type from blocklists, shared distribution infra only) | **Keyword filter lists are NOT blocklists.** They are a distinct data type and a distinct user-facing surface.
They share *only* the signing / sign-verify / publish / subscribe / diff distribution machinery from `BlocklistVerifier`;
the schema, semantics, UI, and user model are all separate. Don't conflate them in code or in product copy. Filter entry shape: `{pattern: String, action:
BLOCK | WARN, warnLabel: String?}`. Multiple subscribed lists merge; strictest applicable label wins for any matched message.
**Two actions, orthogonal to the keyword set:** **WARN** shows the message with a warning banner / collapsed-by-default ("before you tap, this message contains/may contain X");
**BLOCK** prevents the message from being rendered in the UI at all (still relayed normally per the relay-path-never-touches-blocklist rule, just not displayed locally).
Ships with built-in default lists: (a) **slurs** (English first — localisation gap flagged honestly), default BLOCK;
(b) **NSFW text keywords** (sexual content), default WARN; (c) **graphic violence / gore text keywords**, default WARN.
User can promote WARN → BLOCK or demote BLOCK → WARN per list during onboarding and any time after. Custom lists subscribable.
**Per-userId filter exception (important for community use):** every list supports `userIdAllowlist:
Set<String>` so the user can specify "don't apply this filter to messages from this contact." Communities reclaiming slurs internally need this;
misclassified senders need a single-tap "filter exception" path; recovery from a bad subscribed-list ban-wave needs this. UI surface:
long-press a filtered message → "always show messages from this sender." **Auto-intake by publisher (power-mod feature):** mark a publisher's pubkey as "auto-apply everything they sign." When a new filter list signed by that publisher arrives over gossip, it's pulled in without prompt.
Useful for community moderators / curators who maintain canonical lists. Opt-in per publisher;
disclosed at toggle time as "you are delegating filter decisions to <publisher>." **Honest leak note:** subscribing to a list means the gossip layer sees you holding their signed snapshot;
other peers can ask you for it. That advertises which lists you stand by. Two mitigations:
(a) accept as design tradeoff (these are public commitments anyway), (b) per-list "private mode" where you hold the list but refuse to gossip it.
**Distinction matters:** the four content surfaces are (a) text keywords [O67], (b) image NSFW [O81], (c) image gore [O81 — model gap noted, ships text-keyword-only at first], (d) sender identity [BlockManager / O78].
Each carries an independent WARN/BLOCK control. Don't conflate them in UI. Required for App Store 1.2 user-generated-content posture; useful on Android too.
Ported in the merge; UI open.
